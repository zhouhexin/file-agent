# 当前 Harness 逐版本修复与测试流程：大白话说明

日期：2026-11-23。依据当前 `repair_versions.py`、真实规划执行器、评分器，以及本轮 `0001` 的评分导出。

## 1. 先说明现在在运行什么

现在运行的是独立的离线改进实验：根据已有错误生成候选，在测试副本里验证，再使用真实模型对同一批开发题做对照。它没有把候选发布到正式 File Agent，也没有让 WorkBuddy 自动使用候选。

这条实验链有两个阶段，必须分别启动：

```text
阶段一：已有诊断 → 程序分类 → 建议模型提出受限修改 → 程序附带真实契约 → 冻结版本 → 模拟检查

阶段二：你选择已冻结版本 → 明确授权 → 同一批题分别运行旧参考和候选 → 程序独立评分 → 保存各版本结果
```

阶段一不会自动开始阶段二。阶段二结束也不会自动选赢家、留用候选、覆盖参考或上线。当前也不自动把新结果回灌成无限循环；下一批需要明确指定诊断材料、来源、新目录和预算。

## 2. 各部分分别负责什么

| 部分 | 用大白话说明 | 是否会调用真实模型 |
|---|---|---|
| 控制程序 | 读取来源、核验身份、分类错误、管理预算和目录 | 自身不需要模型；按明确授权安排后续调用 |
| 修复建议器 | 根据错误提出一份新的规划说明及受限补丁类型 | 冻结命令明确 live 后会调用 |
| 被测试的规划器 | 回答“用户要做什么、本轮应走哪条路线、用什么参数” | 真实对照命令明确 live 后会调用 |
| 校验器和评分器 | 检查参数、范围、记录和标准答案，重新计算成绩 | 不调用模型 |

模型提出方案，程序决定哪些改动能进入测试。模型不能自己修改评分、题库、权限或预算。

## 3. 第一步：准备固定材料，先检查再付费执行

程序先读四类材料：

1. 旧实验及其已核验的开发题，用来确定要测哪些任务。
2. 固定旧参考方案，用作每个版本的共同对照。
3. 已导出的诊断记录，用来了解哪些调用、参数和意图名称发生错误。
4. 当前真实接口契约，包括允许的意图名称、Tool 输入格式和限制。

冻结和测试的命令都默认只检查，不加 `--live` 不会生成模型请求，也不会创建新实验目录。检查包括来源完整性、文件范围、模型配置、预算和输出目录是否可用。只读检查可能核验 CLI 登录状态，但不等于调用模型生成内容。

题库的人工预期路由等评分依据由可信程序保存，不直接交给建议器当成答案。建议器能看到开发反馈、错误摘要及旧参考，并且不允许把具体题目写成特殊规则。

## 4. 第二步：程序先分类错误

诊断不是简单问模型“你觉得哪里错了”，程序会根据实际记录和输入模型做分类。

- CLI 返回失败、没有完成事件：属于调用问题。连接线索可以记录，但没有证据时不能判断究竟是代理、本机网络还是上游服务。
- 短语超过实际字段长度：属于参数约束问题，使用真实输入模型复现。
- 未经真实澄清就请求展示全部结果：属于跨字段约束问题。
- 模型输出了应用不识别的意图名称：属于意图契约问题。
- 调用失败后由规则生成了 `intent-summary`：记录为兜底行为，不能当成模型主动选择了非法工具。

例如，此前发现的30个参数出错试次包含22个直接报告的未澄清展示全部结果错误和8个超长主题短语错误，部分约束会重叠。程序不通过删除这些记录或放宽限制来提高成绩。

## 5. 第三步：建议模型提出受限修改，程序把契约真正交到候选手里

建议模型生成一份完整的新说明，可以参考旧方案，不能让说明逐代无限叠加。第一批补丁仍只允许修改规划提示字符串常量的追加说明，原系统提示保留；不开放任意函数体修改。

目前有四种类型：

| 类型 | 实际内容 |
|---|---|
| 规划说明 | 模型提出通用的理解任务、选择路线及构造计划的说明 |
| 意图契约 | 程序附带当前真实支持的意图名称 |
| 工具契约 | 程序附带实际短语限制、展示全部结果的前置条件等规则 |
| 两类契约一起提供 | 同时附带意图名称和工具参数规则 |

你本次的 `0001` 是两类契约一起提供。

这解决的是此前的一个交付缺口：过去建议器拿到了名称清单，却可能只写“按 application_contract 选择”；实际规划器的请求里没有同名数据。现在候选的实际系统提示中直接包含准确的名称和约束。

举例，应用识别 `ANSWER_FROM_FILES` 等名称，模型另写成 `ANSWER_FROM_DOCUMENTS` 不会自动等价。新版本把可识别名称直接列出。又如主题短语上限30字符、初次检索不能随意展示全部结果等，都以明确数据提供。

这里是给模型补齐实际可见的信息和约束说明，没有把模型输出自动改成正确答案。真实参数仍会被后端校验，不能靠截断来源名称、伪造澄清ID或悄悄清空字段来通过。

本轮没有把两类契约拆开分别做效果实验，所以不能精确判断哪一条规则贡献了多少提升。

## 6. 第四步：冻结独立版本，再运行模拟检查

每份有效候选有独立版本号，如 `0001`、`0002`。冻结内容包含实际提示、代码差异、来源、模型配置、题目身份和内容散列。散列相当于内容指纹：测试前后发生变化会被发现。

程序随后在测试副本中运行：

1. 编译检查，确认修改后仍是合法 Python。
2. 固定的受保护规划回归，检查原有处理行为。
3. 真实接口约束检查，包括普通查询可接受、未经澄清的展示全部结果必须拒绝、超长短语必须拒绝、允许的意图名称确实能映射。

模拟不调用真实规划模型，也不证明模型已经理解所有业务题。它先确认候选符合允许的修改范围、可运行，并保留原约束。

Windows 使用现有本机 Python、受限候选准入、Python 审计和 Windows Job。当前不是允许模型运行任意 Python 的通用沙箱。

| 状态 | 含义 |
|---|---|
| FROZEN | 版本已保存且通过模拟，可以进入真实对照 |
| GENERATION_FAILED | 该次建议调用失败，没有得到可测试的候选 |
| REJECTED | 提案不符合受限补丁规则 |
| NO_CHANGE | 建议器本次没有提出修改 |
| SIMULATION_FAILED | 已有版本，但模拟未通过，禁止直接真实执行 |
| NOT_GENERATED | 因停止条件等原因尚未生成 |

低分或没有改善不影响已通过安全检查的版本参加真实对照。硬性安全或模拟失败必须标明原因，不能绕过检查。

当前生成协议已修正为 v2：单次可恢复调用失败标记该版本，在原预算内继续下一版；不重试同一版本，也不自动补足成功数量。生成阶段明确识别到认证、权限、额度或限流错误时立即停止。已知旧 v1 的冻结版本继续只读加载，旧文件和旧缓存不改写。

你本次的 `0001` 仍是最初冻结的内容，后续实验管理修复没有把这份候选悄悄换掉。

## 7. 第五步：你指定版本，明确启动真实对照

`repair-test --version 0001` 表示只测试0001；显式 `--all` 表示测试这个批次中全部已冻结的候选。模拟阻塞会明确列出，业务低分不会导致版本被偷偷筛掉。

测试输出使用另一个新目录，冻结目录始终只读。旧参考和候选使用同一份固定模型配置、同一批开发题、相同重复次数。每个版本都对照同一份旧参考；一个版本成绩再好，也不自动成为另一个版本的父版本。

本次是10道题、每组重复两遍：

```text
旧参考：10道题 × 2遍 = 20条测试记录
新候选：10道题 × 2遍 = 20条测试记录
合计：40条测试记录
```

第一次重复每道题先运行旧参考再运行候选；第二次交换先后。两遍用来观察波动，不是两种评分指标。

记录数不等于模型调用数。有的题在固定预检中就返回，不调用模型；有的模型调用失败后转入旧流程，会再产生调用。本次实际账本为39次调用，其中3次失败。

## 8. 单道题在真实测试内部如何运行

以“请根据某份通知说明报名条件，并引用原文”为例：

1. 程序读取这道题已经冻结的原始请求、附件范围和工具目录。
2. 在测试副本中运行真实规划代码，使用旧参考或该版本的候选提示。
3. 模型生成声明式计划，说明任务意图、决策类型、工具和参数。
4. 程序校验结构、工具范围、文件ID和参数。模型不能凭空编造文件身份，也不能执行计划之外的动作。
5. 记录实际采用的路径：候选模型、旧流程回退、规则兜底或固定预检。
6. 把实际路由和决策类型与已冻结的人工预期比较，保存逐题结果。

正文问题通常要保留内容回答目标，即使首步需要用检索发现文件；只返回文件清单不算完成了正确的首轮规划。用户真的只要文件清单时，则应选择文件检索路线。

这里的“真实”表示真实模型和真实规划代码。路由测试不会实际执行业务 Tool 去检索完整材料、生成最终答案或写入 Excel。计划中出现检索或回答工具，不等于工具已经执行。参数合法、路线正确也不等于最终答案已经核实。

## 9. 第六步：程序独立重算，保留所有版本结果

`repair-compare` 不再次问模型，而是读取原始调用、实际规划响应和冻结材料，核对内容身份、顺序、预算与版本，并重放现有规划逻辑重新计算分数。缓存成绩不作为唯一依据。

主要观察四类内容：

- 执行是否完成：计划记录是否全部形成。
- 首轮规划是否正确：路由与决策类型是否匹配预期。
- 契约是否成立：意图能否识别、参数是否合法、有无越权等。
- 成绩来自哪条路径：候选模型成功、回退成功、预检或规则结果不能混为同一件事。

失败、回退和预检保留在完整分母中，不删除。模型不负责给自己打分，程序也不因某版高分自动留用。

以下状态可以同时出现：

```text
流程：COMPLETED，选定版本已测试完。
分数：候选17/20，旧参考3/20。
严格效果判定：INCONCLUSIVE，部分试次没有经过可评估的候选模型路径。
```

当前严格判定沿用原评分器。存在未使用候选提示的预检或调用失败回退时，可能无法给出完整策略有效性结论。它不代表执行尚未完成。

`ALL_SELECTED_VERSIONS_TESTED` 只说明本次明确选中的版本完成；不意味着未生成的0002、0003也已经测试。

## 11. 如何控制时间和费用

每次生成、单版测试或显式整批测试都有自己的明确授权。整批测试的预算覆盖全部所选版本，不能按版本重新发一份总预算。每个试次最多允许既有流程的三次规划请求。

默认连续三次基础设施调用失败停止。失败请求照样记账；未知用量保留未知。额度、时限不足、中断或模拟失败都会保留已有记录，未完成的版本明确列出，不自动重跑。

活动时间包括来源检查、快照和模型阶段等；最终只读独立复算耗时另计。现有实现不能承诺整个进程一定在活动预算到期时立刻退出。比较不新增模型费用，但来源链和文件核验仍可能耗时。

以后再次启动生成或真实对照，必须使用新输出目录。不能在原冻结目录里手动修JSON或补入模型结果。

## 12. 常用命令对应的事情

| 命令 | 做什么 | 何时产生模型调用 |
|---|---|---|
| `repair-freeze` | 诊断、提出候选、冻结及模拟 | 明确加 live 后调用建议模型 |
| `repair-list` | 只读列出各版状态和失败原因 | 不调用模型 |
| `repair-test` | 指定单版、几版或全部冻结候选做对照 | 明确加 live 后调用规划模型 |
| `repair-compare` | 从记录独立重算成绩 | 不调用模型 |

可复制的 PowerShell 命令见[逐版本操作文档](harness-frozen-repair-versions-usage.md)，设计边界见[逐版本实施方案](harness-frozen-repair-versions-plan.md)。本次分析依据为本机 `runtime/repair-score-review-20261123-094319-786078.json`。
