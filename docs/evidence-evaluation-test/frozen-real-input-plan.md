日期：2026-11-05。依据：`File_Agent_Evidence_Evaluator_MVP_Guide.docx`，以及当前评估器、证据回答服务与离线脚本的实际接口。

**2026-11-05实施更新：** 已完成受控采集、同次版本事实复用、输入/金标散列、prepare/confirm/build、隔离evaluate入口、逐轮结果与逐调用回放。使用方法及实际目录见[操作文档](frozen-real-input-usage.md)。下文保留原方案的设计依据；其中“拟新增/尚缺”描述的是开发前状态，已实现项以操作文档为准。历史请求仍不能由日志补成准确快照，真实样本等待重新采集。

**2026-11-09后续研究方案：** 新增[反馈驱动Harness最小闭环方案](feedback-driven-harness-mvp-plan.md)，拟在独立离线实验中研究“LLM提建议、程序受控复测与评分”。本方案原有线上Shadow边界不变；下文“不增加策略调整”仍适用于本次固定输入功能及生产链路，不阻止用户另行授权的离线研究。

## 1. 本阶段要完成什么

先选R001、R016、R034三个真实问题，各固定一份本次实际提供给评估器的输入，再对相同输入重复运行评估。比较标签、理由、引用、失败类别、Token和延迟。

```text
首次取材：真实文件 → 解析/索引 → 检索 → 已授权EvidencePackage
                                         ↓
                              保存证据包、版本事实、时间意图
                                         ↓
复测：固定输入 → 证据状态评估器 → 校验结果 → 对照人工标签 → 报告
```

复测不再次进入规划、检索或最终答案生成，因此无需等待规划阶段，也不会因每次检索片段不同而改变测试条件。真实文件五阶段测试继续保留，用于检验接入与权限；它与固定包评测承担不同职责。

“可重复运行”指相同输入和配置可以被重新执行、结果可以追踪比较，不保证真实模型每次输出完全相同。模型是否稳定，正是需要测量的内容。

本文件是实施方案。本次没有修改应用代码、导出真实EvidencePackage或调用模型，不把现有Excel、日志摘要称为已经冻结的评估输入。

## 2. 当前已经有什么、还缺什么

| 内容 | 当前情况 |
|---|---|
| `EvidencePackage`严格输入结构 | 已有，含问题、范围、证据原文和定位等 |
| 独立`EvidenceEvaluationService.evaluate()` | 已有，可直接消费证据包 |
| 离线`evaluate_evidence.py` | 已有`rules/replay/live`三种模式 |
| 人工标签 | 已按用户确认参考标注40题：29条全0、11条MISSING |
| Shadow日志 | 已有标签、状态、指纹、调用数、Token、耗时和安全错误信息 |
| 真实证据包与同次版本事实导出 | 尚缺受控入口 |
| 历史三题的原始完整输入 | 现有日志不能保证完整还原，不能宣称已具备 |
| 每次重复的独立完整报告 | 当前脚本只保留首轮完整结果，重复轮需补齐 |

当前`三题测试原始核对`、`复测原始核对`等文件保存的是问题、答案、引用和运行信息。**答案引用可能只是输入证据的子集**，并不等于评估器实际收到的整个证据包。JSON文件的名称或格式不能代替内容完整性核验。

可以根据数据库中尚存的证据重建一个新样本，但必须标明“重建”，不能声称逐字复原旧请求。若无法核对全部输入和版本时点，建议重新做一次受控采集，建立新的基线。

## 3. 每个样本必须固定哪些内容

| 固定项 | 具体保存内容 | 为什么需要 |
|---|---|---|
| 问题 | 评估器实际消费的`package.question`，以及原始用户问题 | 同一份证据问对象和问费用，会得到不同缺项结论 |
| 任务形式 | `question_type/answer_mode/response_format/fields` | 普通问答、全文总结、字段表的必要要求不同 |
| 授权范围 | 实际`scope`，来源工作副本或受管修订集合；受控导出来源 | 防止复测偷偷扩大文件范围 |
| 完整证据列表 | 每条原始`evidence_id`、文件/版本/工作副本或修订ID、文件名、`quote`及页码/Sheet/单元格 | 不用摘要或最终引用列表替代原始输入 |
| 限制 | 证据包`limitations`和原有指纹 | 不能把截断或未覆盖的包改成完整包 |
| 版本事实 | 按证据ID保存同次核验的`VERIFIED/UNVERIFIABLE`及`current_version_id`，另附核验时间和就绪依据 | 离线复测不去查后来发生变化的数据库当前版本 |
| 时间意图 | 评估调用实际使用的`CURRENT/HISTORICAL/UNKNOWN` | 原始问题与规范化模型问题可能不同 |
| 人工金标 | 三类问题、应缺哪些事实、冲突维度、相关证据ID、解释与标注依据 | 用来判断正确，而不是只判断返回成功 |
| 运行条件 | 模型及服务别名、提示词/代码版本、温度、字符/输出/调用/超时/重试限制、批处理配置、依赖版本 | 区分输入变化、代码变化和模型变化 |

不得只保存文件名、文件路径、最终答案或一个指纹就称为冻结。不得随意改写quote、重排证据列表、重新分配证据ID、补入模型上次没收到的段落；这些动作会产生新输入版本。

API key、JWT、数据库口令、客户端对象和运行时服务不进入快照。实际调用仍从本机私有env读取授权配置。包含真实正文的输入快照保存在Git忽略的本机测试目录，不写普通JSONL日志，也不放入AgentGraphState。

## 4. 建议的本地数据组织

下面目录是拟建结构，本次尚未生成这些数据文件：

```text
runtime/evidence-test/datasets/frozen-real-v1/
  manifest.json                    # 数据集版本、输入散列、采集来源与代码/配置说明
  cases.json                       # 现有CLI兼容的数据集入口，由受控转换生成
  inputs/
    R001.package.json              # 实际EvidencePackage
    R001.versions.json             # 同次后端核验的版本事实
    R001.context.json              # 原始问题、实际时间意图、来源运行ID和采集时间
    R016.*
    R034.*
  annotations/
    gold-v1.json                   # 人工金标和解释，始终与模型输入分开
  runs/
    baseline-live-01.json           # 每轮完整记录，不覆盖旧报告
    baseline-live-02.json
    baseline-live-03.json
    format-regression-01.json       # 固定响应/故障回放报告
```

`manifest.json`中每条样本需保存两类标识：

1. 原有`evidence_fingerprint`：沿用生产链路，便于对应日志。
2. 完整输入散列：对问题、全部证据、版本事实、限制及时间意图作确定性序列化后计算SHA256。对象键排序，数组顺序与字符串内容保持不变。

现有生产指纹不能单独证明问题一致：已观察到R001与R016共用证据指纹，但问题与预期标签不同。完整输入散列必须覆盖问题与实际评估上下文。金标另有版本/散列，模型配置另有版本，避免把改标签混成改证据。

## 5. 怎样获得真实快照

### 5.1 采集位置

工作副本与受管源两条链都已调用`EvidenceAnswerService._evaluate_shadow()`。在这里，`EvidencePackage`已经生成，并带有后端确定的允许工作副本/修订集合，最适合增加仅测试环境使用的受控采集能力。

建议固定顺序：

1. 明确选择案例和允许对象，完成原有权限与证据范围校验。
2. 从现有只读版本读取器取得版本事实。
3. 把传入的package、同次版本事实、原始问题和实际时间意图导出为快照。
4. 本次评估也消费这份同次版本事实，避免导出和评估分别查询数据库、跨过一次版本更新。
5. 写出输入散列和采集来源，采集成功后锁定这版文件。
6. 继续原有Shadow及回答流程；导出失败单独记录，不改变原回答或变更权限边界。

这需要小范围开发。不能在模型内部自行访问文件或查询数据库，也不能通过SQL写入伪造版本关系。版本事实核验失败时如实保存`UNVERIFIABLE`；不能为了得到COMPLETED改成VERIFIED。

### 5.2 如何控制采集范围

采集默认关闭，仅允许独立测试环境明确选定R001/R016/R034等案例，限定输出到测试目录。不能自动导出所有用户对话。正常Shadow日志继续只存指纹、受控状态和错误摘要。

采集文件采用先写临时文件、校验后发布的方式，不覆盖已经冻结的版本。受控导出只保存已授权的数据，本地冻结包也不是访问实时生产文件的凭据。

### 5.3 后端版本校验与离线快照的区别

真实请求使用`AuthorizedVersionReader`执行权限、对象绑定、活动状态、当前版本索引等检查。离线复测使用冻结结果，不连接实时数据库。

因此离线版本规则测试不能代替真实权限集成测试。OUTDATED正例若来自构造快照，必须明确其测试层级；只有真实版本链采集到的快照，才能说来源于真实版本事实。

## 6. 怎样冻结人工标签

现有Excel是针对限定原文件设计的预期，采集后仍要检查实际包是否包含同样的支持信息：

- R001：对象、两种培训时长、截止时间均进入包时，语义预期无缺项。
- R016：对象可定位，但包内没有每人培训费金额时，预期MISSING，缺少的事实必须写明。
- R034：包内应能核对1—2年培育、立项周期、2000元/项及预算模板/支持额度差别。题目问“是否提供申请预算”，回答未提供可满足这个子问，不能机械贴MISSING。

如R034实际包遗漏了必要的培育段落，应把“原文件预期”与“实际包金标”分别保存，并记为检索差异；不能偷偷补入该段后仍沿用旧输入散列。

只知道`issue_types=MISSING`或`REQUIRED_FACT_UNSUPPORTED`还不够。需保存内部评估结果中的requirements、缺失事实、可比维度、理由、evidence_ids和限制，供受控本地人工复核。自由业务理由保存在私有评测报告，不写普通运行日志。

金标不发送给真实模型。用户确认参考答案并授权助手标注的来源应保留，不虚构独立复核者。后续人工纠正金标时发布gold-v2，并对所有比较版本重算分数。

## 7. 三种测试分别证明什么

| 模式 | 输入 | 模型是否重新调用 | 能说明什么 |
|---|---|---|---|
| `rules` | 固定包和版本事实 | 否 | 版本规则和结果聚合是否正确；不测语义识别 |
| `replay` | 固定包、版本事实与固定响应 | 否 | 校验器/协议/错误处理是否可回归；不证明模型准确率 |
| `live` | 固定包、版本事实与固定运行配置 | 是 | 真实模型面对同一输入的标签、解释、稳定性、成本与延迟 |

“离线评测”表示不走实时规划/检索/回答链路；`live`仍会连接已配置的外部模型并计费，不是断网运行。

真实模型重复运行时，不能复用上轮语义结果缓存。每轮结果独立保存。固定响应回放则必须确实复用同一返回，二者不能混算。

格式截断、空内容、超时等故障可建立独立确定性fake用例，不应将人工编写的响应冒充从历史线上真实捕获的响应。对多批调用，需按调用序号和请求散列回放各批响应；不能给每批复用一个不匹配的固定响应。

## 8. 现有CLI如何复用，以及需要补齐的细节

当前入口：`apps/api/app/scripts/evaluate_evidence.py`。

它已有`--dataset/--mode/--repetitions/--output`，可以复用；但有以下限制：

1. `EvaluationCase`要求`case_id/group/package/versions/expected_issues/expected_explanation/recorded_semantic_response`。现有Excel或`已标注样本-v1.json`不能直接传入，需要受控转换。
2. `recorded_semantic_response`目前所有模式都必填，尽管rules/live不用它。拟改为仅replay必需，不能为通过结构检查胡填一个“正确模型响应”。
3. 真实链路会额外传入由原始问题推断的`temporal_focus`，而CLI目前直接从package.question推断。拟允许读取采集时冻结的实际时间意图，特别是全文总结问题被规范化的情形；不允许LLM自行改写该值。
4. `versions`的键必须覆盖实际输入全部evidence_id。缺少键或核验信息必须报错/无法核验，不补成正确版本。
5. 当前重复运行只保存首轮完整结果，其他轮只参与成本和稳定性统计。拟保存每条、每轮的完整结果；未完成前，正式三轮对照可用三个独立`--repetitions 1`报告。
6. 当前live报告固定写“合成样本”，使用真实数据集时应根据来源输出准确说明。
7. 指标需要同时呈现失败和PARTIAL。空标签且失败，不能算正常通过；没有阳性样本的Recall显示N/A；引用集合精确匹配与标签是否检出分开报告。
8. 输入散列、数据集版本和实际运行配置应与每轮报告关联。修改模型、提示词、输出上限或代码后建立新实验版本，不覆盖原基线。

数据文件生成、人工复核完成后，可以从项目根调用现有规则测试。以下命令的前提是`cases.json`和输出目录已真实生成，**现在不能把它当成开箱即用的真实数据测试**：

```bash
PYTHONPATH=apps/api /opt/homebrew/anaconda3/envs/py311/bin/python \
  -m app.scripts.evaluate_evidence \
  --dataset runtime/evidence-test/datasets/frozen-real-v1/cases.json \
  --mode rules --repetitions 1 \
  --output runtime/evidence-test/datasets/frozen-real-v1/runs/rules-01.json
```

live运行应复用独立测试启动器的环境隔离办法，仅加载`runtime/evidence-test/.env`，不沿用终端里的旧模型或数据库变量。当前启动器尚无离线评测子命令；实施时补此入口，再提供用户可直接执行的命令，不让用户手工拼接含密钥的环境变量。

## 9. 最小执行顺序与交付物

### 第一步：先采集三题

交付三个真实包、同次版本事实与时间意图、来源记录、manifest散列。没有采集到的样本标“待采集”，不由最终答案反推补齐。

### 第二步：复核三题金标

以实际包核对Excel预期；说明缺失项和引用。保留原题干，不能为消除UNKNOWN偷偷增加“当时”再说是同一历史输入。需要明确时间的对照题可另建case-v2。

### 第三步：不调用模型的检查

验证输入结构、证据ID唯一与引用白名单、版本键覆盖、散列匹配。运行rules，并对已记录/明确构造的固定响应做replay故障回归。确认不读写真实文件、不查询变化中的数据库、不影响原答案。

### 第四步：单独跑三轮真实模型评估

相同输入和配置，每轮单独报告。先复测R034的截断问题；若改变输出上限或模型参数，单独命名实验，与原配置比较。失败样本保留在报告中，不删除、不记正常。

### 第五步：再扩大到60条

三题闭环稳定后继续采集现有40题，补足正常、MISSING、CONFLICT、OUTDATED覆盖及指南要求的故障/权限边界用例。真实材料没有冲突或真实版本链时如实记录缺口，明确构造、真实版本回放与前端五阶段的测量层级。

## 10. 每轮应能回答哪些问题

- 用的是哪一个数据集、金标、输入和模型配置版本？
- 每题缺什么、哪两条证据为什么冲突、哪个旧版本被哪个当前版本替换？
- 错在模型调用、JSON/Schema、证据引用、语义判断还是版本不可核验？
- 同一输入三轮是否一致；是否只是三轮都失败？
- 每题各次调用的Token、调用数、延迟、用量是否完整？
- Shadow开/关时既有答案、原有工具调用和权限行为是否一致？

现阶段只评估与解释，不增加自动补检、拒答、改文件或反馈驱动的自动策略调整。规划耗时作为真实五阶段链路的独立指标保存，不计入固定包评估器延迟。
