# 第四阶段：自动判断效果，并决定是否继续试

日期：2026-11-11。状态：最小开发及工程验收完成，真实模型优化效果待live测试。

## 要解决什么

补丁能运行不代表答得更好。这一步由补丁之外的独立程序打分，再把失败信息交回Harness，形成“看问题→提修改→试跑→打分→再改”的流程。

## 准备怎么做

1. 用同样的问题、附件、模型设置和重复次数，分别重新运行原版和修改版。两组只有获准代码不同。
2. 人工正确答案只由外部评分程序读取。试验进程和补丁模型不能读取或改动答案、测试规则和评分器，也不能靠自报“成功”过关。
3. 逐题比较分数，检查正常题有没有退步、文件范围和危险操作限制有没有被破坏，同时统计每类Precision/Recall/F1、Token和耗时。
4. 自动给出“改善、没收益、退步、无法判断、实验无效”。模型没正常返回或大量用了备用规则时，不能冒充已经验证补丁没用。
5. 把可信的失败摘要交给下一轮，避免原样重试已验证无效的补丁。预先设置最大轮数、总请求数、总等待时间和无进展次数；默认一轮，显式设置后可多轮。所有阶段、所有轮次共用预算。
6. 找到达标改善、模型建议不改、预算耗尽、连续失败或多轮没进展时自动结束，保存原因。中断不自动重发已付费请求。

每个候选都与同一冻结基线比较，不把前轮补丁悄悄叠到下一轮。开发期间用假模型验证至少两轮，确认下一轮确实读取前轮反馈。真实运行需显式live，预算内无需逐轮人工确认。

## 怎么验收

- R002能进入正文回答/找证据路线，SEARCH01继续正常找文件。
- 修改版所有预定轮次都正确、至少一题优于原版、没有题目退步，并通过第三阶段回归和安全检查，才算这组题上的达标改善。
- 假模型覆盖改善、无收益、退步、模型失败、结果被篡改、预算耗尽和中断；费用未知时写未知。
- 最终记录明确展示改了哪些代码、两组分别得多少分、花费多少、为什么停止。真实无改善也如实保存，不修改人工答案强行过关。

## 完成后有什么、还没有什么

四阶段完成后，Harness可以在允许的代码范围内自动提出、执行和验证修改，并在总预算内继续尝试。通过后自动保留候选补丁，不自动合并或上线。

R002与SEARCH01仅用于验证首轮路由闭环，尚不能证明检索和最终回答都正确。扩大使用范围还需增加独立保留题，不能一直用反复调过的两题证明泛化效果；保留题的逐题答案不交回模型继续调参。
