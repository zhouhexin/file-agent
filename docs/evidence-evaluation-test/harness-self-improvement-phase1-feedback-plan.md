# 第一阶段：先让Harness看懂“为什么失败”

日期：2026-11-11。状态：最小开发及工程验收完成。

## 要解决什么

以前记录“答错了”，Harness仍不知道该改哪里。这一步要把失败拆开说清楚：是模型没返回、模型理解错了，还是模型理解正确，却被程序带进了错误分支。

例如R002：模型已经决定读取通知并回答正文，后面的程序却把它改成了找文件。SEARCH01本来就只要求找文件，不能把它也当作错误。

## 准备怎么做

1. 读取已有实验，核对输入和记录没有被改过。
2. 把每题的模型判断、程序最终选择、模型调用是否成功、是否使用备用规则，整理到一份机器能读取的JSON文件。
3. 有证据的写成事实；可能的原因写成待验证判断；旧记录没保存的内容就写“缺少记录”，不能补猜。
4. 以后新运行时补齐这些诊断信息。普通日志只记编号、状态和耗时，不写原文、答案或密钥。

文件名为`root-cause-feedback.json`。另外生成给补丁建议模型看的安全版本，不包含人工正确答案（Gold）、身份、文件正文或密钥。第一阶段在现有路由实验之后增加整理步骤，不改用户实际走的业务分支。

## 怎么验收

- 能区分v2的“模型调用全部失败后用了备用规则”和v3的“模型理解正确却被后端改了方向”。
- 不把正常找文件误报；没有证据时允许写“不确定”。
- 原实验和人工答案保持不变；检查发现记录被改过时拒绝使用。
- 开发用固定假模型做测试，不产生新的真实模型费用。

## 完成后有什么、还没有什么

完成后Harness可以读取失败依据，尚不会修代码。下一步按[第二阶段](harness-self-improvement-phase2-patch-plan.md)生成补丁。四阶段目录见[首页](README.md)。

首批只检查“请求走哪个分支”，暂不评价文件有没有真正找到、答案是否完整。模型调用失败时保留实际路由分数，但不能据此认定某个模型提示方案已被证实无效。

## 本阶段已交付

新增`routing/diagnostics.py`记录离线规划轨迹，`improvement/feedback.py`把已核验实验整理成机器反馈，接在原路由结果之后。已用旧v2/v3生成反馈：v2识别调用失败，v3保留模型与后端方向不一致的事实；旧规则轨迹缺失会说明。使用方法见[操作步骤](harness-self-improvement-usage.md)。

建议器改进后，新增v2反馈，将独立评分得到的“任务正确/错误/未评分”与执行状态分开，并标明提示策略/代码补丁实验。旧v1仍可按旧协议校验，再在内存从原始实验重建新摘要，不回写历史。详见[改进方案](harnessdev-advisor-prompt-recommendation.md)和[新版复测步骤](harness-self-improvement-usage.md#10-建议器现在怎样区分没收益和没错误)。
