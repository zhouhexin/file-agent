# 第二阶段：让Harness自己提出“代码该怎么改”

日期：2026-11-11。状态：最小开发及工程验收完成，真实模型生成效果待live测试。

## 要解决什么

现在的Harness只能从开发者预先写好的方案中选一个。这一步让模型根据失败记录和相关源码，自己提出实际代码修改。

模型写的是“建议补丁”，程序负责检查和执行。不会让模型直接操作终端、数据库或当前项目目录。

## 准备怎么做

1. 读取[第一阶段](harness-self-improvement-phase1-feedback-plan.md)的失败记录。
2. 由程序提供相关源码，并固定允许修改的位置。第一版只允许调整`agent/planner.py`里“正文问答与找文件谁优先”的那一处判断条件，其他分支不能动。
3. 模型可以回答“不改”，也可以返回修改前后的判断条件、理由和所依据的反馈编号。程序把这些修改生成真正的代码差异文件`candidate.patch`。
4. 检查修改是否针对本轮源码、是否超范围、是否偷偷写死题号/文件编号。判断条件只允许现有变量、受控枚举和简单布尔比较，不能增加任意函数调用或执行动作。
5. 保存模型实际建议、补丁、检查结果、调用次数、Token和耗时。生成失败就记失败，不自动无限重试。

建议模型看不到人工正确答案、评分代码、密钥或整个文件库。模型额度由启动实验的人固定，模型不能自行加预算。修改检查只证明“范围符合要求”，效果要等后面测试。

## 怎么验收

- 能用假模型生成可用补丁，也能返回“不改”。
- 改错文件、改其他分支、基线不一致、引用不存在的反馈、硬编码样本等都被拒绝。
- 模型超时、输出被截断或格式错误时，留下明确失败记录。
- 当前项目源码、旧实验和人工答案保持不变。

## 完成后有什么、还没有什么

完成后能拿到模型自主提出的补丁，尚未运行补丁。下一步交给[第三阶段](harness-self-improvement-phase3-isolation-plan.md)。

真实模型生成需要显式使用live模式；开发验收只用假模型。本阶段不会把人工预写修复冒充模型自动生成。

## 本阶段已交付

新增`improvement/schemas.py`和`patches.py`，在建议模型与执行器之间检查修改。`self-propose`可单独生成补丁，`self-cycle`会自行生成本轮候选。已验收合法修改、不修改、错误基线、越界代码、样本特例及生成失败，实际步骤见[操作说明](harness-self-improvement-usage.md)。

建议协议已扩展为v2：分别记录问题分类、简短事实、修改假设和不修改原因。建议器保留NO_CHANGE权利；与已知任务错误矛盾的“没有问题”或没有有效代码历史的“已经证伪”会保存明确拒绝码，不强制生成补丁、不自动重试。执行范围及预算不变，参见[本次改进方案](harnessdev-advisor-prompt-recommendation.md)。
