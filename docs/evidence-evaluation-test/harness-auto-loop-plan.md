# 一次启动：探索、固定复测、读取结果再探索

日期：2026-11-18。按修改前冻结方案完成实现及工程验收。未启动真实模型。

## 1. 用大白话说明

用户一次指定总请求数、总时限和最多循环次数。程序让建议模型探索不同候选，按原研究规则挑前K份，冻结原样复测，再把复测记录自动交回下一轮建议器。每轮完整留档，最后独立比较；合格入选仍可能为空。模型自己决定策略，程序只负责顺序、预算、隔离和裁判。

新增`campaign-loop`及`campaign-loop-compare`。旧探索、复测、比较和锁定入口保留。默认只检查，显式live才开始；本次开发不跑真实模型。当前仍只优化初始规划提示，不扩展生产修改权限。

## 2. 统一预算与冻结

- 默认最多2个循环，最多3个；每循环默认探索6份，每题每组1次，前2份各固定复测5次。可显式调整，但沿用原候选数、次数和输出额度范围。
- 整个任务共用明确的总请求额度（最多5000次）、总时限（默认14400秒、最多28800秒）；任何阶段只获得剩余额度和剩余时间，不按循环重置。历史费用单列，不算本次新授权。
- 10题、2循环、6份探索、前2份复测5次的保守调用上界是1932。允许更小预算，先耗尽即停止。预算单位仍是Codex调用而非不可观测的内部HTTP次数。
- 复测期间不调用建议器、不改候选；只有该阶段封存后才生成下一份。所有控制组、失败、回退、未知Token及原始调用保留。

## 3. 如何把反馈接回去

从已完成的开发复测或原C/搜索开始。下一轮探索以最近已封存阶段为来源，复用有界历史摘要和当前完整反馈。历史按真实依赖顺序排列，保证新的开发复测位于旧搜索之后，不再用“直接依赖数量”冒充先后。

已经在当前循环或起始开发复测测过的策略引用，不再进入本任务的研究复测选择；完整记录仍给建议器。新复测按原研究资格筛选未测策略，而不是强制模型产生更好结果。若没有新的值得复测候选，记为跳过并把探索结果继续反馈，尊重无进展停止条件。

## 4. 什么情况下结束

达到原严格入选条件，停止并报告候选及其复测来源，供后续正式锁定和保留验收；不自动上线或使用保留题。模型选择不修改、达到最大循环或连续无进展次数、总预算/时间耗尽、异常或中断也停止。一次局部高分不算严格通过。

研究进展按开发对照正确率差的最好观察衡量，仅用于无进展计数；不能替代最终严格评估。R035预检等限制继续如实参与，允许最终没有合格方案。
