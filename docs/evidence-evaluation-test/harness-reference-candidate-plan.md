# 保留旧方案的自动改进测试

日期：2026-11-20。

## 1. 目标与实现边界

旧方案保留为固定参考，不把旧成绩当成当前环境的成绩，也不把旧方案直接发布为生产策略。先在当前环境对照原始提示与旧方案，再主要从当前保留方案生成完整替代说明；允许少量从原始提示重新探索。新方案未通过时，保留方案不变。

新增独立的 `reference_loop.py`，复用现有来源核验、受限提示构造、执行器、预算 Journal、配对评分及 Windows 本机隔离。通过现有 `campaign-loop --reference ...` 选择新模式；不传该参数时保持旧流程。这样不用改写旧实验协议、旧评分或历史文件。新增模式使用独立协议及控制器源码身份，比较命令按协议分派。

## 2. 来源和首次对照

操作者通过 `--source` 指定已有的开发实验，通过 `--reference` 指定旧方案所在实验。原 C 验证实验直接读取其冻结候选；开发迭代或复测批次必须同时给出 `--reference-round`。先独立核验两条来源链，确认开发输入、Gold 和业务源码快照一致。确认/保留实验不允许作为优化来源。

历史 Profile 不同只能在显式 `--allow-model-profile-change` 后开展新实验。所有新对照组使用同一个当前 Profile，不比较不同时期的裸分数来决定替换。来源文件不修改、不移动；新目录保存旧说明全文、提示身份和来源完整性引用，不保存保留题。

首次固定对照为“原始提示 vs 旧方案”，重复次数取 `--retest-repetitions`。无论旧方案是否严格合格，都如实记录并可作为研究起点；合格与研究参考必须区分。对照未完整完成时停止，不能跳过首次对照直接生成候选。

## 3. 生成与测量

每轮建议器看完整保留说明、首次旧方案说明、当前完整开发反馈和有界历史摘要。`inherit` 从当前保留说明修改；`fresh` 从原始提示探索；默认 `mixed` 每四份候选安排一次 fresh，其余为 inherit。fresh 也必须看到旧方案并与当前保留方案比较。

模型返回完整的新说明，允许删改，不是把新文本无限追加在旧文本后。原系统提示逐字保留，新说明仍最多 3000 字符，沿用样本泄漏、命令文本、AST、文件和进程限制。每份候选保存父版本、生成方式、修改差异、完整说明和提示散列。

新模式连续无进展最多容许 `max_no_progress × max_no_progress_cycles` 份候选；CLI 将前者设为每循环候选上限，成功替换后清零。规则在执行前冻结，不能为了多试几份而临时增加预算。

探索对照为“当前保留方案 vs 新候选”。初测有配对正确数提升时才固定同一候选进行重复复测；即便初测存在违规，也只可作为研究信号，复测不能冒充通过。初测与复测均完整保存失败、回退、预检和未知费用，样本不得删除。复测不调用建议器。

## 4. 保留与替换

沿用原 `score_round` 的严格判断。只有完整复测为 IMPROVED、无新增任务/契约退步、所有试次可评估、没有候选违规，并且每次重复的候选正确数都严格高于对照，才把候选设为本次研究的下一轮起点。模型失败、预算耗尽、中断、同分、分数下降或不满足检查均不替换。

固定旧方案永久作为参考，不随起点更新而覆盖。研究起点的更新不等于正式上线；输出始终 `automatically_adopted=false`。保留集不执行。没有合格新候选时明确报告未找到，不把旧参考包装成已验收成果。

## 5. 预算与审计

首次对照、建议、初测和复测共用一个 Journal，总请求数和时限不按阶段重置。继续使用既有单次调用和 Token 上限。复测最多顺序处理每循环 top_k 份有提升信号的候选，不增加第三组，也不复用历史旧分数替代当前测量。默认不调用真实模型，显式 live 才执行。

独立比较器重建来源、实际建议输入、候选、父版本、生成顺序、两组快照、固定回归、真实请求、每次配对分数和替换决定；不能信任缓存成绩、缓存赢家或重封后的汇总。中断和不完整试次仍计入分母。记录、预算和顺序不一致时拒绝整个实验。

## 6. 验证与交付

使用确定性模型替身验证：首次对照在建议之前；完整旧说明确实进入建议输入；生成方式按固定规则切换；候选不会无限累加；较差/同分/回退/违规候选不替换；合格提升后下一轮使用新起点但旧参考仍保留；预算和中断不丢记录；篡改父版本、请求、快照、成绩及替换记录均拒绝；CLI 默认零调用；既有流程继续通过。

真实 Windows 本地执行器另做至少一次真实子进程专项，模型仍用替身。本轮不启动真实付费实验，不更新生产配置，不提交 Git，不改已有 runtime 实验。
