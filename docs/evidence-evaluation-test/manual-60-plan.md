# 60 条真实材料证据评估：人工构建与计分方案

配套表格：[manual-60-template.xlsx](manual-60-template.xlsx)。

这份方案用于你自行上传的真实材料，沿“上传文件 → 解析正文 → 建立全文索引 → 检索证据 → 证据状态评估”测试。表格已安排 60 个场景、预留三轮共 180 次记录，但**没有替你填写真实文件、人工正确标签或模型结果**。已有的 64 条合成回归案例不算这 60 条真实材料验收样本。

## 1. 一条样本到底是什么

一条样本不等于一份文件，而是下面这一组固定信息：

> 一个问题 + 本次实际送入评估器的原文证据包 + 文件版本事实 + 人工正确标签和理由。

同一份通知可以用来问“培训地点是什么”，也可以问原文未提到的“是否提供住宿”，形成不同样本。不要只改问法、文件名，就把大量重复内容当成独立样本。

建议从不少于约 10 个文件族选材料，例如培训通知、照片归档通知、项目申请与批复、费用明细、会议安排、报名要求、制度修订等。一个文件族指同一业务对象的一组相关材料，不等于文件格式。优先选可正常提取文字的 PDF、DOCX、XLSX、TXT；扫描件和旧 Office 转换问题可以另外记录，避免把解析失败误认为评估器判断错误。

| 计划组别 | 数量 | 人工正确标签：MISSING / CONFLICT / OUTDATED |
|---|---:|---|
| 证据完整且一致 NORMAL | 15 | 0 / 0 / 0 |
| 缺少关键证据 MISSING | 15 | 1 / 0 / 0 |
| 同口径证据冲突 CONFLICT | 15 | 0 / 1 / 0 |
| 当前问题引用非当前内容版本 OUTDATED | 15 | 0 / 0 / 1 |

这里的 NORMAL 是测试时派生的类别，程序没有新增名为 NORMAL 或 SUFFICIENT 的评估状态。程序报告的是问题标签集合，以及 COMPLETED、PARTIAL 等执行状态；二者不能混为一谈。

为了让第一次报告容易看，主集尽量按上表选单一问题标签。真实材料确实同时缺信息、又有冲突时，三个标签都必须如实填写，不能为凑每组 15 条删掉正确标签。可以把它放进额外的多标签挑战集，再换一条单标签材料补足主集；也可以保留，但必须说明各标签实际阳性数可能不再都是 15。

## 2. 先统一人工判定口径

### NORMAL：关键事实都能找到，差异可以解释

问题要求的每项事实都能在实际证据包里定位，而且没有同口径矛盾或不当旧版本引用。至少放入以下反例：

- 申请金额与批准金额不同：两个阶段，不应单凭数字不同报冲突。
- 批准预算与实际支付金额不同：两个口径。
- 不同学院、项目、批次、年份的数字不同：对象或时间不同。
- 1 万元与 10000 元：换算后相同。
- 历史问题明确问“按当时规定”，引用当时版本：不应报 OUTDATED。
- 原文出现“不修改原文件”等否定句，但另一个句子明确支持要问的事实：不能把整页都当成否定。

### MISSING：问题必需的信息在本次证据包中找不到

先把问题拆成明确的必需事实，建议每条 1～5 项，本轮不要超过当前评估协议最多 8 项的范围。例如：培训对象、至少派几人、时间、地点。

逐项填写“哪条证据支持”；真的没有支持时，写清缺哪项。标注范围是**本次送给评估器的证据包**，不是你知道的全部文件，更不是最终答案写了几项。

- 原文件有地点，但检索包没取到地点：对这个包可以标 MISSING，同时把根因记为检索漏召回。
- 原文件和证据包都有地点，但最终回答漏写地点：是回答完整性问题，不能据此把评估金标改成 MISSING。
- 只有申请表，却问“最终批准金额”：缺批准结果，不是申请数字与未知批准数字冲突。
- 正文写“日期待定”：能支持“尚未确定”，不应机械当作完全没有该字段。遇到含义不清，先标“需仲裁”，不要强行归 MISSING。

“旧通知今年是否继续执行”需要新的适用依据。找不到依据可以是 MISSING；文件年份早本身不能证明技术版本 OUTDATED，也不能证明业务规定已经失效。

### CONFLICT：必须先证明两条证据可以比较

把冲突双方写成下面的对照表，五个维度相同且数值或结论不相容，才标 CONFLICT：

| 维度 | 要核对什么 |
|---|---|
| 对象 entity | 同一项目、学院、人员、活动或同一份事项 |
| 属性 attribute | 都在说批准金额、截止日期、地点等同一属性 |
| 时间 time | 同年度、同批次、同场次、同一统计时点 |
| 口径 basis | 单位、币种、含税范围、总额/人均、统计人群相同 |
| 事实阶段 fact_status | 都是申请、批准、实付或最终结论中的同一阶段 |

此外，要排除“后一份明确更正或替代前一份”的情况。更正前后不同可以是正常更新，不能把它无条件当成两份同时有效的矛盾结论。

为了隔离 CONFLICT，优先用两份独立且均为各自当前版本的记录，正文明确同对象、同口径，又没有替代关系。人工理由必须列出双方原文和页码/单元格，不能只写“两个数字不同”。

如果真实材料里找不到 15 组明确冲突，就如实保留缺口。需要可控难例时，可以另存脱敏测试副本，在副本中仅改变一个事实；但必须标“脱敏派生”，与原始真实冲突分开报告，不能伪称业务材料本来有矛盾。不要覆盖真实原件或在共享工作副本上直接制造矛盾。

### OUTDATED：查的是内容版本替换，不是文件年代

正例需要同时满足：

1. 服务端能确认同一逻辑文件的版本关系。工作副本通常绑定同一 Document 的不同 DocumentVersion；受管源文件则沿同一 ManagedFile 的真实修订链核对。
2. 引用的内容版本 ID 与当前内容版本 ID 不同；不能靠文件名“新版”“最终版”或 UUID 大小来推断。
3. 当前版本已有成功的当前索引，后端能核验这条版本事实。
4. 问题明确问当前状态，实际证据包却仍引用旧内容版本。

以下均不能直接算 OUTDATED：两次上传成两个独立文件、文件年份较早、只改文件名或移动目录、新版还没有索引完成、用户本来就在问历史情况。

**当前普通前端会优先检索当前版本，没有供用户指定“这次故意引用旧版”的测试按钮。因此，仅用前端上传提问，不能保证构造出这 15 条正例。**

建议分两层准备：

- NORMAL、MISSING、CONFLICT 优先做真实五阶段测试。其中 N09“历史问题引用真实旧版”也需要能取得旧版证据的回放条件，不能保证全部 45 条都能只靠普通前端完成。
- 15 条 OUTDATED 准备真实旧版、新版、版本链和已就绪索引后，通过受控的版本证据回放验证。当前缺少对应导出/回放入口时，先标“待准备”，不要手改数据库去伪造完成。

现有离线脚本允许使用冻结版本快照验证规则，但快照不是数据库真实版本链的证明。由真实材料整理的冻结包可以作为“冻结证据测试”，构造的版本 ID 只能算“构造版本测试”。它们与真实五阶段、真实版本回放分别报告，不能把混合的 60 条都宣称为前端全流程验收。

当前时间意图识别还有一个边界：明确的“当前/现在/最新/现行/目前”可识别 CURRENT；“当时/历史/旧版/四位年份”等可识别 HISTORICAL；二者混写可能得到 UNKNOWN，“今年”单独出现也不保证识别为 CURRENT。OUTDATED 主测试用选中文件限定范围，再问“按当前版本……”，历史反例用“按当时版本……”。若要覆盖自然语言歧义，另列挑战项，不能把当前启发式漏识别伪装成已支持。

## 3. 60 条样本分配清单

下列是选材任务，不是已经存在的真实证据。表格中已逐条预填相同的 ID 和建议场景。每条都需要你补真实问题、证据位置和人工标签。

### 3.1 NORMAL：15 条，其中包含容易误报的反例

| ID | 选材或提问方向 | 重点防止的误判 |
|---|---|---|
| N01 | 单份通知明确对象、人数、时间、地点 | 完整证据误报缺项 |
| N02 | 两份记录说同一事实且一致 | 多文件误报冲突 |
| N03 | 相似题名，不同学院/项目，金额不同 | 混淆对象 |
| N04 | 同项目申请金额与批准金额不同 | 混淆事实阶段 |
| N05 | 批准预算与实际支付不同 | 混淆财务口径 |
| N06 | 不同年份同指标数值不同 | 混淆时间 |
| N07 | 万元与元换算后相等 | 混淆单位 |
| N08 | 总额与人均金额不同 | 混淆统计口径 |
| N09 | 明确历史问题，引用当时旧版 | 旧版一律判过期 |
| N10 | 存在旧版，但实际引用当前版 | 看见旧版就报过期 |
| N11 | 同页有无关否定句，目标事实有明确正向依据 | 否定范围过大 |
| N12 | 多页合起来完整支持问题 | 跨页支持误报缺项 |
| N13 | 有明确对应关系的同一对象简称/全称，事实一致 | 别名误判 |
| N14 | 申请条件和最终审批结果不同，分别回答 | 条件与结果混淆 |
| N15 | 不同批次或场次的时间、地点不同 | 混淆批次 |

### 3.2 MISSING：15 条，明确缺的是哪一项

| ID | 选材或提问方向 | 应缺的信息 |
|---|---|---|
| M01 | 询问申报截止日期，正文未提供 | 截止日期 |
| M02 | 询问适用对象，材料只有办理流程 | 适用对象 |
| M03 | 问时间与地点，实际证据包只有时间 | 地点 |
| M04 | 问至少派几人，材料只说“派员参加” | 明确最低人数 |
| M05 | 问精确金额，数字没有可确认的单位 | 金额单位或口径 |
| M06 | 对比两个年度，只给其中一年材料 | 另一年度数据 |
| M07 | 问批准金额，仅提供申请材料 | 批准结果 |
| M08 | 问 A 学院，却只有 B 学院证据 | A 对象的支持证据 |
| M09 | 问当前是否继续执行，仅有历史通知 | 当前适用依据 |
| M10 | 问负责部门，材料没有责任归属 | 负责部门 |
| M11 | 正文要求参考附件，附件未提供且正文无该细节 | 附件中的必需事实 |
| M12 | 只有目录/摘要，没有要问的具体正文事实 | 对应原文事实 |
| M13 | 同问 3～5 项，其中一项确实没有支持 | 某一必需事实 |
| M14 | 表格所问字段为空，也没有其他说明 | 所问字段值 |
| M15 | 问提交邮箱，只有联系人电话 | 提交邮箱 |

M03 如果只是最终答案漏地点，而包里明明有地点，应移回 NORMAL，另外记回答缺漏。M05、M14 遇到可推导单位或明确“待定”的情况，要重新核对，不能机械按本清单贴标签。

### 3.3 CONFLICT：15 条，双方均须提供原文定位

| ID | 同对象、同时间、同口径下的矛盾属性 |
|---|---|
| C01 | 同项目同年度的最终批准金额不一致 |
| C02 | 同批次最终截止日期不一致 |
| C03 | 同一场次的最终地点不一致 |
| C04 | 同一要求的最低参加人数不一致 |
| C05 | 同期间同口径实际到账金额不一致 |
| C06 | 同一时点同一资产范围的数量不一致 |
| C07 | 同批次同人群的资格要求互斥 |
| C08 | 同一活动最终票数不一致 |
| C09 | 正文明示只有一位的负责人，却记为不同人 |
| C10 | 同条件下“必须提交”与“不需要提交”相反 |
| C11 | 同一场次最终开始时间不一致 |
| C12 | 同一考核项的最终权重不一致 |
| C13 | 同学院同年度同口径获批项目数不一致 |
| C14 | 两份并行最终记录中的同一报价不一致 |
| C15 | 三份记录中两份一致、一份矛盾 |

C15 要求至少识别出一对真正矛盾的证据；不能强制模型必须引用全部三份，才承认“识别到冲突”。标签是否检出与证据对是否准确，分开检查。

### 3.4 OUTDATED：15 条，需要版本回放条件

| ID | 当前问题实际引用的版本情形 |
|---|---|
| O01 | v2 已为当前且就绪，仍引用 v1 |
| O02 | v3 已为当前且就绪，仍引用 v2 |
| O03 | 有多次更新，仍引用更早版本 |
| O04 | 旧 PDF 页面的证据 |
| O05 | 旧 Word 段落的证据 |
| O06 | 旧 Excel 单元格的证据 |
| O07 | 旧 TXT 段落的证据 |
| O08 | 同一受管源文件旧修订的证据 |
| O09 | 同包混有旧版与当前版，相关事实数值一致 |
| O10 | 版本发生了内容更新，但所问字段值未变 |
| O11 | 同一年内的旧版，不能只看年份 |
| O12 | 文件显示名称相同，但内容版本不同 |
| O13 | 旧文件名带“最终版”，仍有真实后继版本 |
| O14 | 新版修改其他章节，所引用章节未改 |
| O15 | 多个已授权文件中，只有一个引用旧版 |

这里检查的是“当前问题引用了被替换的内容版本”，所以字段数值没变也仍可报技术 OUTDATED。O09 优先选新旧相同事实，避免同时产生 CONFLICT；所有 OUTDATED 样本也应检查是否意外缺项。格式变化、改名本身不能充当真实内容更新。

## 4. 人工构建的操作顺序

### 第一步：复制空白模板，整理材料清单

把模板另存到 `runtime/evidence-test/datasets/manual-60/` 等本机私有目录。原始文件保持不变。填写文件族、素材来源“真实/脱敏派生/构造版本测试”和测试层级“五阶段/冻结证据包/真实版本回放”。

不要求准备 60 份文件；要求 60 个有独立测试目的、能复现的案例。一个文件族同时提供正反例很有帮助，但如果后续拆开发集和验收集，要按文件族分开，避免相同正文泄漏到两边。

### 第二步：明确范围与问题

每条写出唯一、完整的问题，明确对象、时间和金额口径。通过选中文件或已有受控文件选择方式固定范围，不能假定“当前会话”一定排除了其他共享材料。

例如可使用下面的句式，但括号内容须来自你的真实材料：

> 只根据所选的两份文件，分别列出【项目】的申请金额与批准金额，并给出原文依据。

> 只根据所选材料，【活动】的对象、最低参加人数、时间和地点分别是什么？没有明确依据的项请直接说明。

> 按当前版本，这个事项的【目标字段】是什么？请列出原文依据。

先人工列出必需事实，而不是看模型回答后再决定本来想问什么。

### 第三步：完成上传、正文与索引检查

沿用[独立启动方式](standalone.md)和[真实文件步骤](real-files.md)。等候文件成功处理、正文可读且索引完成，再发问题。记录 Document/工作副本/内容版本等稳定标识，不以相似文件名代替对象身份。

解析失败、索引未完成、选错文件、未形成证据包应记在对应环节。它们是整个流程的问题，不能悄悄删掉；也不能据此认定评估器已经正确判断 MISSING。

### 第四步：先冻结人工答案，再评分

要分清两种测试：

- **固定证据包测试**：先固定问题、实际证据、版本事实和人工标签，再让评估器处理同一包，最适合比较评估器本身。
- **真实五阶段测试**：先根据限定材料人工写下预期与理由，再执行。检索结果出来后，由复核者按实际证据包核对。若实际包与预设包不同，保留原预期、另记检索差异；用于评估器计分的金标仍以它实际收到的包为准，且复核者应先看原文、不看模型标签。

当前 shadow 日志有证据 ID/指纹等摘要，**不保存全文证据包**。如果无法从已有引用、受控读取或审计信息还原实际包，就先标“需仲裁”，不要把最终答案的引用列表直接当作全部输入证据。需要严格的固定包反复测试时，仍需受控导出/回放入口；这份文档和 Excel 没有增加该功能。

每条人工填写：三个 Gold 0/1、逐项支持或缺失说明、冲突双方定位、版本关系、标注者、复核者。达成一致后设为“已冻结”。能找同事复核最好；只有自己时，隔一段时间盲看原文再复核，并在报告写明单人标注。

冻结后模型错了不能反过来改金标。确实发现人工标注错误，可以仲裁后升级数据集版本，保留修改理由，并对所有被比较的模型重新评分。

### 第五步：先跑完整一轮 60 条，再做两轮稳定性复测

每次记录同一次运行的 `agent_run_id`，用它关联日志，不要混用两次提问的数据。在项目根查看：

```bash
rg --no-ignore -n -F 'evidence_evaluation.shadow' runtime/evidence-test/logs/
```

再以记录的运行 ID 缩小范围：

```bash
rg --no-ignore -n -F '<替换为实际agent_run_id>' runtime/evidence-test/logs/
```

取 `evidence_evaluation.shadow` 的 `issue_types`、`status`、`version_status`、`semantic_status`、错误、限制、Token 和延迟。`MODEL_JSON_OBJECT` 只说明返回 JSON 可解析，不能当成正确识别。

同样输入再测两轮，用来观察同一题是否忽好忽坏。固定问题、证据指纹、模型版本、配置和数据集版本；若证据指纹变了，先检查是否检索输入变了，不要把输入变化全部归因于模型波动。180 次执行依然只有 60 个样本，不是 180 个独立样本。

### 第六步：把错误归到正确环节

| 现象 | 优先核对的环节 |
|---|---|
| 文件里有内容，解析正文没有 | 解析/OCR |
| 正文有内容，实际证据包没取到 | 检索或截断 |
| 包里有内容，评估说缺失/冲突判断错误 | 证据评估 |
| 包里完整、评估无缺项，但最终回答漏写 | 回答生成或结论支持性校验 |
| 超时、额度不足、返回格式不符 | 模型调用/协议 |
| 版本无法核验或时间意图 UNKNOWN | 版本事实/意图识别边界 |

例如最近的声像档案系统培训通知：原文和输入证据已有对象、人数、时间、地点，最终答案却漏了地点。不能把这个现象直接记成评估器的 MISSING。再如历史照片归档通知没有新一年的执行依据，也不能只因题名含旧年份就标 OUTDATED。

## 5. 每条记录填什么

### 样本标注页：模型运行前应尽量固定

| 字段 | 填法 |
|---|---|
| ID、计划组别、建议场景 | 已预填；计划组别不是人工金标 |
| 文件族、素材来源、测试层级 | 用于说明样本独立性和真实/派生/回放边界 |
| 文件与版本清单、引用/当前版本 ID、索引就绪 | 填可核验的事实，不靠文件名猜 |
| 问题、必需事实与口径 | 用最终要测试的原句；每个事实说明对象、时间、口径 |
| 证据 ID 及页码/单元格 | 正例写原文定位；缺项写其他证据为何不能支持 |
| Gold_MISSING / Gold_CONFLICT / Gold_OUTDATED | 数字 0 或 1，NORMAL 全 0；不要留空却设冻结 |
| 标注理由、标注者、复核者、标注状态 | 复核完成才设“已冻结” |

真实原文片段可以在私有证据附件中另存，并在该页写相对文件引用。对固定包测试，建议同时保存受控导出的 EvidencePackage JSON 和服务端核验版本事实；不要自行编造真实对象的版本关联。

### 测试记录页：从同一次评估中抄入

| 字段 | 来源/说明 |
|---|---|
| 样本 ID、轮次 | 已预留 1～3 轮 |
| 时间、agent_run_id、模型/评估器/数据集版本 | 保证同一次运行可追溯 |
| 证据指纹 | shadow 的 `evidence_fingerprint`；用于核对输入是否一致 |
| 执行方式 | LIVE 真模型；REPLAY 固定返回；RULES 规则。后两者不计入模板的真模型指标 |
| 评估/版本/语义状态 | 对应 shadow 的 `status/version_status/semantic_status` |
| 预测三个标签 | `issue_types` 出现填 1；完整返回且明确未出现填 0；失败未判断的留空 |
| error_codes、limitation_codes | 如实抄录，不因有 COMPLETED 就忽略错误或边界 |
| 输入/输出 Token、Token 用量完整 | shadow 的 `input_tokens/output_tokens/token_usage_complete` |
| 评估延迟 ms | shadow 的 `duration_ms`，不是整个 Agent 的耗时 |
| 备注 | 检索差异、回答漏项、回放来源、未触发原因等 |

如果未形成证据包而没有 shadow，测试记录填 `NOT_TRIGGERED`，这是本表自定义的测试记号，不是程序新增状态。子检查被跳过按实际填 NOT_EVALUATED，不补写成成功。

## 6. Precision、Recall、F1 怎么算

对 MISSING、CONFLICT、OUTDATED 分别做“是否检出这个标签”的统计。每个标签都要检查全部 60 条：既看它的 15 条正例，也看其余 45 条是否误报。

| 项目 | 大白话 |
|---|---|
| TP | 人工说有这个问题，模型也报了 |
| FP | 人工说没有，模型却报了 |
| FN | 人工说有，模型没报出，包括失败/弃权导致没有检出 |
| Precision = TP / (TP + FP) | 模型报出的这个问题，有多少是真的 |
| Recall = TP / (TP + FN) | 实际存在的这个问题，模型找出了多少 |
| F1 = 2TP / (2TP + FP + FN) | 同时衡量乱报和漏报 |

举例仅为说明公式：15 条真实 CONFLICT，模型找对 12 条、漏掉 3 条，并在其他样本上误报 2 条，那么 Precision=12/14≈85.7%，Recall=12/15=80%，F1=24/29≈82.8%。这不是本项目实测结果。

NORMAL 另作派生统计：人工三个问题标签全 0；预测要求评估总状态和版本、语义两个子检查都 COMPLETED，且三个预测标签全 0。PARTIAL、空结果、失败不能自动成为 NORMAL。为避免正常文件因时间未知全部无法完成版本检查，主集应把当前/历史时间意图写明确；不要为拿分事后改问题。

模板自动计算上述四类 P/R/F1、四类 Macro-F1，以及正常样本误报率。没有预测阳性时 Precision 显示 N/A；没有真实阳性时 Recall 显示 N/A；F1 直接按公式计算，分母为 0 才显示 N/A。

### 失败和 PARTIAL 不能从报告里删掉

本表用较严格的主口径：已执行、人工金标已冻结的 LIVE 记录都参与评分。真实问题未检出，包括调用失败导致没检出，计 FN。PARTIAL 已可靠检出的标签仍可按对应标签计 TP/FP，其余未检出不作成功结论。失败的负例不是“正确无问题”，也不能变成预测 NORMAL。

同时必须报告：执行覆盖率、完整评估率、EVALUATION_FAILED 比例、PARTIAL 比例、未触发比例和错误类别。标签指标本身不会惩罚所有负例弃权，因此不能只给 P/R/F1 就声称系统稳定。如果另给“仅完成样本的准确率”，注明它是条件指标以及剔除了多少条，不能代替主口径。

还应逐条核对定位质量：MISSING 缺的是否是用户必需事实；CONFLICT 指出的证据对是否真正可比；OUTDATED 是否引用正确的旧版本。仅检测到同名标签，不代表解释和引用一定正确。精确引用集合匹配与标签 P/R/F1 是两个不同指标。

## 7. Token 和延迟怎么记录

**统计一次证据包评估的总开销，不是把一个包内每条引用重复算一次。** 如果评估器分批调用，取该次 shadow 已汇总的输入/输出 Token。

- 总 Token = 输入 Token + 输出 Token，仅在 `token_usage_complete=true` 时视为完整可比。
- 用量未知留空，完整标记填 FALSE；不要因日志默认数字为 0 就断言超时调用没有消耗 Token。
- 不把 Planner、检索意图识别、最终回答等其他调用混进评估器 Token；若需要总流程成本，另开一列记录。
- 不用返回字符数估算已计费 Token，也不从 reasoning 字符长度推算。供应商没有返回完整用量时明确记“未知”。
- 评估延迟用 shadow 的 `duration_ms`；包括该次评估内版本/语义检查的实际等待。整轮 Agent 可能还包括检索和回答，不能混作评估延迟。
- 超时、失败的耗时也保留。没有进入评估器的记录，评估耗时留空，不能填 0 拉低平均值。

至少报告平均总 Token、Token 用量完整率、平均评估延迟、P50、P95。P50 是一半评估在这个时间内完成；P95 是 95% 在这个时间内完成。平均成本与延迟同时列样本数，必要时按四类分别汇总。

三轮逐轮报告，不把重复调用直接合并成更大的独立样本集。可另记“三轮标签集合一致的样本数/60”和“三轮都完成的样本数/60”；三轮都失败即便结果一致也不代表稳定识别。

## 8. 表格使用与正式报告

Excel 含四页：

1. **使用说明**：填表规则。
2. **样本标注**：60 行建议场景；人工金标目前全部留空。
3. **测试记录**：180 行，第一轮先填完整，再做复测。
4. **指标汇总**：B1 选 1、2、3 查看对应轮次；灰色公式格和隐藏辅助列不需要手填。

表格公式只统计 LIVE、已经执行且金标已冻结的记录。LIVE 可能来自前端或真实模型固定包调用，因此**汇总页不自动证明这些都是五阶段样本**；必须结合“测试层级”和“素材来源”分层报告。固定返回 REPLAY 的高分不能冒充模型识别能力，RULES 不能衡量语义判断。

只有已冻结 60 条且本轮参与评分 60 条，才可以写“60 条测试结果”。版本回放入口尚未就绪时，按实际完成数写“已完成若干条真实五阶段，OUTDATED 正例及 N09 版本反例待测”；若使用冻结快照补测，则写清两层各自规模，不称全部为真实版本集成验收。当前 Excel 不是离线脚本 `--dataset` 所需 JSON，也没有新增 Excel 自动转换或旧版本注入功能。

建议正式结果采用下面的结构：

| 类别 | 实际阳性数 | TP | FP | FN | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|---:|---:|
| NORMAL | 待测 | | | | | | |
| MISSING | 待测 | | | | | | |
| CONFLICT | 待测 | | | | | | |
| OUTDATED | 待测 | | | | | | |

表下补：真实/派生材料数量、五阶段/固定包/真实版本回放数量、已冻结与已执行数、执行与完整评估率、失败/未触发/PARTIAL、正常误报率、平均 Token、用量完整率、平均/P50/P95 延迟，以及三轮一致性和典型错误。

每类只有 15 条，漏一条就会让该类 Recall 变化约 6.7 个百分点。这一规模适合发现问题和建立回归基线，不能证明所有学校业务场景已达到稳定高准确率。根据这 60 条反复修过代码后，它们就成为开发回归集；要确认泛化效果，应再留一批不同文件族的新材料独立验收。
