# 开发集自主调整、逐次冻结测试、保留结果并选优

2026-11-17补充：候选数量、初测重复数与研究复测现按[多候选探索及固定复测方案](harness-exploration-retest-plan.md)实施，原最终推荐门槛保持不变。本文三候选参数描述对应旧版协议。

日期：2026-11-16。状态：已实现实验管理、冻结选优、锁定与独立确认入口，完成Fake及真实OS工程验收；未发起新的真实模型调用。真实选优仍须满足原严格门槛，当前R035的范围限制见第5节。

## 1. 目标用大白话说是什么

让Harness使用现有开发题自己分析失败、修改允许调整的策略、提出不同方案。每个方案先固定下来，再完整测试；测试过程中不能边看分数边改方案。测试结束后保存全部结果，交给Harness作为下一次调整的依据。最终按事先定好的标准，比较多个方案，选出有证据支持的较好方案。

候选改得不好时，由建议模型继续分析和调整。开发者只维护实验管理、冻结、预算、隔离和独立评分，不把某道错题的修复逻辑人工塞进候选。

“最终选优”允许返回“没有合格候选，保留原版”。模型没有义务为了交差编造修改，程序也不能为了选出一个冠军放宽门槛。

## 2. 什么叫每次测试都冻结Harness

冻结的是这一轮正在被测试的完整候选版本及其测试条件，不是让优化永远停止。

| 测试开始前固定的内容 | 为什么固定 |
|---|---|
| 原版代码快照、候选补丁、完整规划提示和允许调整范围 | 明确测的到底是哪一份方案 |
| 题干、实际附件与上下文、开发标签、Tool Catalog | 防止改题、补造输入或换工具后假称方案改善 |
| 模型、Provider、接口及可观测生成参数 | 原版和候选采用相同条件；无法控制的模型随机性用重复测试观察 |
| 建议器版本、外层实验程序、评分标准与门槛 | 候选不能在考试时修改自己的裁判 |
| 重复次数、试次顺序、总请求额度、总时限和停止条件 | 防止挑最好的一次或中途追加预算 |

冻结后登记版本和散列；测试结束再次核对。发现候选、输入或执行条件变动，本批结果标为不可比较，不能混入排名。服务端模型权重和CLI内部HTTP次数等不可观测部分如实标明，不能声称可以完全控制。

建议器只能在两批测试之间生成下一份候选。候选生成与候选测试是两个独立阶段。测试过程由可信程序执行，模型不能改参数、权限、Gold或计分方式。

## 3. 实验循环

```text
冻结开发集、原版、允许调整范围、评分及总预算
→ 独立核验已有实验，只导入开发题历史
→ 建议器读开发失败、已尝试方案及结果
→ 自主提出新候选，或有依据地选择不修改
→ 检查候选是否在允许范围内
→ 注册候选版本并冻结本批测试条件
→ 同一开发集上重复测试原版和候选
→ 独立重放与评分，保存本批所有结果
→ 建议器读取这些结果，自主决定下一份候选
→ 到预先约定的停止点后，统一比较候选
→ 冻结入选方案，执行独立确认测试
→ 输出推荐候选，或保留原版
```

下一份候选可以改进前一次方案，也可以放弃前一次思路。当前允许范围仍为原规划提示末尾的一段通用说明；它替换上一份追加说明，不无限叠加。具体文字由模型生成，不提供人工预写答案或固定修复选项。

外层建议器和实验管理版本在同一批实验中固定。当前没有开放“模型任意修改建议器、裁判、预算或整个仓库”。如需扩大允许调整范围，必须另建实验协议，不能夹在本批里改变。

## 4. 每次留下什么结果

每批都用全新私有目录，已有封存实验保持原样，不在里面继续写文件。跨实验承接通过来源路径、完整性身份和只读重建实现。

- 候选编号、来源批次、模型生成的假设、原始建议及精确映射后的结构。
- 原版及候选的源码/提示身份、真实补丁、冻结条件和输入身份。
- 每道题、每次重复的实际计划、正确与否、参数错误、意图契约、实际执行模式及回退。
- 模型调用成功与失败、脱敏错误、已知Token、未知费用次数和耗时。
- 独立分数、退步项、可比较范围、为何继续或停止、是否达到入选条件。
- 对下一批可用的开发反馈，以及当时已经尝试过哪些方案。

失败、无收益、不修改、被拒绝、中断和未运行都要保留，不能只保存成功记录。未知Token不能当零；模型失败和固定预检结果不能包装成候选提示的成功。

当前`adaptive-iteration-v2`的两轮候选及结果都已保存在各自`rounds/`目录，可作为后续开发历史来源。需要先独立核验，再导入；不能靠缓存中的REGRESSION或某个孤立patch文件判断。

## 5. 怎么选一个较好方案

选择标准在候选生成前固定，统一展示全部候选及原版，不在每轮看到结果后改排序规则。

1. **先看是否有资格参加比较。** 候选在允许范围内，源码和输入身份一致，保护检查通过，预定试次和模型条件可核验。无法归因的回退、固定预检、模型失败及缺失试次保留在报告中，不偷偷删除。
2. **执行原有门槛。** 有效配对退步、应用意图契约退步、权限或参数违规等仍按冻结规则处理，不为了选优放宽。
3. **比较业务正确率及重复稳定性。** 保留逐题、逐次明细，不把一次偶然正确当成稳定改善。
4. **在业务表现相近时再比较Token和耗时。** 费用不完整时明确不可直接比较，不能把调用失败造成的低开销当优势。
5. **对初步入选的同一候选另做冻结确认。** 不重新调用建议器生成“差不多”的新提示冒充复测。

停止搜索时应依据事先约定的候选数、总预算、连续无进展、基础设施失败或合理NO_CHANGE。不能只因第一份候选稍有改善就把它说成多个方案中的最佳；也不能在模型明确不改时强迫继续生成补丁。

当前R035持续走固定预检，该分支不由可修改的提示控制。对当前冻结题库和仅追加规划提示的范围，现有严格“全部实际使用Adaptive”门槛会阻止整体合格判定。本方案不删除R035、不改其标签或悄悄降低门槛。可以展示“现有观察中分数较高的方案”，但没有满足冻结验收条件就不能称为已验证推荐。若要改变可优化范围或评分协议，须在新的实验开始前单独定义和审查。

## 6. 开发题负责调整，保留题负责最后检查

开发题可以反复用于生成反馈，模型可知道开发任务对错。随着多轮优化，开发分数可能过拟合，因此开发集优胜本身不代表一般可靠。

现有四道保留题不参与候选生成、逐轮排名或反馈历史。先根据开发集选定一个候选，再锁定它做最终保留验收；不能在保留题上反复挑冠军。保留题逐题结果若用于继续改策略，该批题就不能继续声称独立，需要另备保留题。

目前测试范围是初始规划。入选结果只代表这个范围的能力，实际检索、证据评估和最终回答仍须另行验收，不自动更新正式服务。

## 7. 现有实现能做什么，还缺什么

| 能力 | 当前情况 |
|---|---|
| 开发反馈驱动模型生成不同候选 | 已有；真实v2完成两轮 |
| 每轮保存建议、补丁、源码副本及逐题结果 | 已有 |
| 固定候选在原版/候选之间受控测试 | 已有，1—3次重复可配置 |
| 单次运行的统一预算、停止及独立核验 | 已有，最多3个候选轮次 |
| 当前运行内把刚测完的结果传回建议器 | 已有 |
| 从已结束的迭代实验承接完整开发历史 | 已补：`campaign-run`支持C、已封存迭代或本类批次，并只读核验历史 |
| 保持搜索记录并在批次结束后统一选优 | 已补：首个改善不提前停止，全部记录参与按条件区分的统一比较 |
| 从迭代注册表锁定入选候选并接独立确认/保留验证 | 已补：`campaign-lock`和`campaign-confirm`提供独立新入口，旧C导入入口保持原协议 |

这些能力由新增实验管理入口提供，旧`adaptive-iterate`仍保持原有单批停止和来源语义。实现只补历史导入、候选注册/冻结、统一比较及确认接口，不人工编写业务候选，不把笼统建议失败自动当成业务程序缺陷。

## 8. 后续最小落地顺序与验收

先实现只读导入已有迭代历史、候选注册和冻结清单，使每批测试能够明确承接开发历史；再实现批次级统一比较、入选方案锁定及独立确认入口。新协议与旧实验分版本，已知旧宿主只读重建，不编辑历史或放开任意执行器身份。

验收用Fake模型证明：多份候选可按固定条件重复测试；未完成评分前不能提出或应用下一份候选；全部结果可追溯；候选与冻结输入篡改会被拒绝；排名由独立程序按预先规则重算；不选择仅因失败而便宜的方案；可以没有赢家；保留题不流入开发反馈；中断及总预算跨批次承接仍可审计。对模型的业务建议不设置“必须包含某个修复句子”的测试。

真实运行前先展示候选数、题数、重复次数、建议与规划的调用上界、总时间和费用可观测性，再由操作者明确本批预算。没有新的具体预算和显式live启动，不自动继续收费搜索。方案阶段曾仅新增本文档；按后续明确授权完成的入口开发及验收见第10节，旧实验仍保持原样。

## 9. 本次入口开发范围（代码修改前冻结）

用户已明确要求新增入口。本次补齐以下命令，旧迭代入口保持原语义：

- `campaign-run`：`--source`可为已完成C、迭代或本类实验，`--history`可额外指定历史；先独立核验，承接开发反馈、已尝试说明及结果。默认零调用检查，显式live才执行。
- `campaign-compare`：零调用重算历史绑定、每轮冻结、全部分数和统一排名。
- `campaign-lock`：只对达到原有严格门槛的入选候选创建独立锁定产物，原实验不修改；没有合格候选则拒绝锁定。
- `campaign-confirm`及`campaign-confirm-compare`：只运行锁定的一份候选，明确选择开发确认或保留验收，不调用建议器，单独授权新预算，不把结果回送优化入口。

搜索仍最多三份新候选，每份至少重复两次，沿用现有可修改范围、schema及独立评分。遇到第一个改善不提前结束；仍尊重NO_CHANGE、重复候选、无进展、基础设施故障、人工中断和预算停止。旧失败候选也进入历史，不能伪造已排除的策略或只留下成功。

原版与每份候选从同一源码快照构造，候选生成后保存`frozen-evaluation.json`，绑定源码清单、完整提示、输入与Gold身份、模型Profile、建议器身份、评分版本、预算和固定试次顺序；测试结束保存封存标记，再把独立结果交给下一轮。比较器重建这些内容，不能仅相信冻结文件自报的散列。

排名保留所有已核验候选，历史候选只有在输入、原版、执行Profile、重复数和评分语义一致时才能与本批直接比较；其他候选只作历史观察。候选须满足原有严格IMPROVED门槛且实际重复至少两次才有推荐资格。排序依次为正确率、全次正确的题目数量、完整可比的Token总量及延迟，最后用稳定候选ID打破完全并列；缺失费用不当零。没有资格者可展示“最佳观察”，但不得锁定为推荐。

新批次的显式额度覆盖本次所有建议和规划，轮次间不重置。已结束历史的请求和耗时单独列示，并给出累计请求数，避免把新授权当作旧实验自动续费。历史导入有数量和递归深度限制，拒绝循环依赖及保留确认产物。旧v2宿主按已核验身份只读重建，未知身份不放宽。

实现复用原迭代执行器、全局Journal、OS隔离和逐题重放；新增实验管理与确认模块，不修改实际Planner、Tool schema或Gold。新增Fake测试及真实OS专项，默认检查使用用户已完成的`adaptive-iteration-v2`，不发起真实模型调用。最终操作文档给出全新实验目录及完整启动命令。
