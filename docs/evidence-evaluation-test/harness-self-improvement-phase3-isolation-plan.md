# 第三阶段：把补丁放到独立环境试跑

日期：2026-11-11。状态：最小开发及本机真实系统隔离验收完成。

## 要解决什么

模型写出的修改可能有错。这一步给它准备一个受限制的试验区，让试错不会影响当前项目、已经启动的服务、原文件和人工答案。

## 准备怎么做

1. 复制本轮真实使用的源码作为基线，记录每个文件的校验值。当前尚未提交的代码也要纳入，不能只拿Git里旧版本来测试。
2. 从同一基线建立原版和修改版，只有修改版应用[第二阶段](harness-self-improvement-phase2-patch-plan.md)通过检查的补丁。
3. 执行程序预先固定的语法检查和路由回归检查，模型不能自己挑命令、跳过测试或改测试答案。
4. 用macOS自带的系统隔离限制试验进程：不给密钥、不给人工答案、不准自由联网、不准修改试验区之外的文件，也不准启动其他程序。
5. 设置等待时间和输出大小上限，超时或中断就停止并保存记录。隔离不可用时明确停止，不偷偷换成普通子进程继续跑。

独立目录或Git worktree只解决“在哪里试”，本身不等于已经限制了访问权限。本机隔离功能必须实际验证。首版使用现有Python环境，不安装新服务。

## 怎么验收

- 原版和修改版来自同一份实际源码，差异只有获准补丁。
- 正常补丁能试跑；语法错误、回归失败、超时和中断有记录。
- 实际尝试越界读写、读取人工答案/密钥、自由联网和启动其他程序，确认会被阻止。
- 试验前后，当前源码、原文件、业务数据库和旧实验保持不变。

## 完成后有什么、还没有什么

完成后知道“补丁能不能正常运行”，是否真的改善交给[第四阶段](harness-self-improvement-phase4-acceptance-plan.md)。

实验只生成首轮计划，不执行真实文件操作。后续live请求通过外部可信程序统一发送和计费，试验进程拿不到模型密钥。在已授权范围和预算内，不需要每轮再由人点一次确认；正式上线另行审批。

## 本阶段已交付

新增`improvement/isolation.py`、`worker.py`和`executor.py`。已验证当前macOS环境可以编译和执行完整规划，并阻止越界读写、联网和启动其他程序。固定回归保护普通找文件、明确附件、缺源改名、分类及带年份检索。首版仅支持macOS，其他环境或隔离不可用时停止；操作见[测试步骤](harness-self-improvement-usage.md)。

## 本次修复：试验进程不再寻找真实配置

真实测试发现：隔离副本运行时，日志等公共组件会调用默认配置加载器，向上找到`runtime/evidence-test/.env`后被系统拒绝读取。这是执行环境的问题，不能据此判断候选补丁是否有效。

修复在隔离启动环节完成：宿主明确传入固定的假数据库地址、仅本次临时目录内的日志路径和legacy规划设置；worker在导入规划、日志等业务组件前，给当前独立进程安装这份配置。所有组件的`get_settings()`都返回同一份已验证测试配置，不读取环境变量、不寻找`.env`。真实模型密钥仍只留在宿主，普通API/worker配置加载方式不变，系统隔离权限不放宽。

验收增加三项：上级存在带诱导配置的`.env`时仍能完成固定检查和两轮Fake复测；传入缺项、额外字段、真实数据库/密钥或越界日志路径时明确拒绝；直接读取上级`.env`仍被系统阻止。保留原`self-live-v1`，真实复测使用新目录`self-live-v2`，开发不调用真实模型。
