# WorkBuddy 手工补全 Excel 回传

## 目标

用户下载已发布的同名 `.xlsx`，手工补全现有记录后作为本轮 WorkBuddy 附件上传。服务器以完整文件名唯一解析活动数据集，冻结当前 DocumentVersion/SHA/revision，校验上传文件，再给同一 WorkingCopy 发布新 DocumentVersion 和 StructuredDatasetExport。不可变旧版本继续保留，不产生第二个活动目标，不重新 OCR 或追加来源成员。

## 契约与边界

- WorkBuddy 仅从本轮受信提交单收一份 `.xlsx`，任务文字明确包含同一完整文件名；不把它当普通新目标归档。服务器对文件名、当前版本、请求键和上传哈希做固定校验。
- 仅补全已有记录的单元格及工作簿格式；不允许清空既有非空格、改变目标表标题/列结构、增加未登记的人员行、新增或改写公式、引入外部链接。需要新人员时继续使用现有 PDF/Word 追加流程。其他工作表可保留和补充，但目标表 schema 必须不变。
- 使用已有 36 MiB 请求、32 MiB XLSX 和有界 OOXML 预检；上传正文只在服务端临时文件处理，Tool 回执不包含本机路径或单元格全文。
- 本轮人工单元格变动及对应记录 ID/行号保存在任务审计载荷，结构化查询投影以已发布的人工修订覆盖旧展示值；原来源证据和旧版本不修改。正式发布采用 `stage_publication` / `finalize_publication`，数据库当前版本与可见同名文件不一致时维持门禁并恢复。
- 相同 request_key + 文件哈希幂等复用；基线版本、SHA 或 revision 已变化则拒绝上传并要求基于最新版重做。

## 验收

同名目标只剩一个活动 WorkingCopy，新旧不可变文件均在；当前下载与上传字节一致；后续追加保留人工补充；结构化查询显示已补值；旧版、清空/新增人员、改标题、公式和无效 XLSX 均被拒绝；发布失败仍可通过现有恢复器补发且不重复创建版本。

## 2026-09-29 实施与验证

已新增 `manual-revisions/publish` API、复用现有发布协调器的人工修订服务、WorkBuddy `excel_manual_revision_checkout/publish` MCP 工具和独立 Skill。未增加数据库表；已发布人工修改摘要存于现有 `structured_dataset_tasks` 审计载荷，结构化查询按修订号投影，原提取事实仍保持不可变。工具要求回传编辑前 checkout 的版本 ID、SHA 和 revision；同一提交单请求键可幂等查询结果。

后端/MCP 相关回归 48 项通过；针对当前 `申报人员业绩汇总-教学科研型教授.xlsx` 的隔离副本试填 J5 并验证，候选校验成功且服务器已发布原文件哈希不变。WorkBuddy 0.1.53 安装包已生成；真实宿主会话上传需在部署 API/MCP、安装插件后验证。

## 可见文件被直接编辑后的回传

若用户在服务器的同名可见工作副本上直接补充，文件 SHA 会先于版本记录变化。普通按文件名读取与来源追加仍拒绝此状态，避免把未发布编辑当成正式版本。人工回传仅在本轮受信上传文件的 SHA 与可见文件完全一致、编辑前冻结的 DocumentVersion/SHA/revision 仍为当前基线、上传文件通过结构和单元格差异校验时继续发布。上传文件与可见文件不同则返回 `MANUAL_EXCEL_VISIBLE_CONFLICT`，不覆盖任何一方。发布任务记录提交前的可见文件 SHA，便于审计。

回归测试包含服务器可见文件先被补全后再上传相同文件的成功发布、上传另一份文件时的冲突拒绝及旧版本保留。相关 API/MCP 测试 49 项通过；WorkBuddy 插件包升至 0.1.54。
