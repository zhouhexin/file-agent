新入口暂命名为 `excel_writeback_*`，旧 `structured_dataset_*` 工具和服务端导出原样保留。为避免在同一目标上出现两套互相矛盾的行数据，首版继续使用现有 `StructuredDataset`、`StructuredDatasetMember` 和 `StructuredDatasetTask` 作为稳定 ID、候选证据和短期占用记录：WorkBuddy 回传完整 XLSX，服务端仍执行原有逐字证据/审批与字段规范化校验并登记成员，但跳过旧服务端 Excel writer；再比较回传文件的新增单元格与已校验的展示值，匹配后发布为新的 `DocumentVersion`。任务进行时使用既有 `active_task_id` 拦住旧 append/export；结束后两条入口可在同一版本链上继续，不允许并发各写一份当前文件。这个选择保留服务器证据审计，不要求另建一套真相表。

首版的 checkout 只接受已经归档且已注册的数据集目标 `.xlsx`。本轮新上传 `.xlsx` 可由新 MCP 工具在内部调用现有受控注册入口后 checkout；`.xls` 必须先走已有的受控异步格式提升并核验，再对提升后的 `.xlsx` checkout，不能让 WorkBuddy 在旧二进制格式上直接覆盖。此限制不会改变旧链路，也不能被描述为已支持任意 `.xls` 的直接原样写入。

## 1. 目标与边界

让 WorkBuddy 负责读取用户材料、决定单元格内容、在受控工作区内实际修改 Excel，并把完整结果文件回传；File Agent 不再根据候选字段重新生成同一张 Excel，而负责身份、证据、目标版本、文件差异、安全检查、原子发布和版本审计。这样用户看到的仍是服务器文件列表中的一个同名当前工作副本，可以下载并持续追加。历史内容仍通过同一个 Document ID 下的 DocumentVersion 管理，不新增可见的“版本后缀文件”。

这不是“WorkBuddy 上传任意 Excel 就覆盖服务器文件”。服务端必须验证它基于哪一个当前版本修改、哪些单元格改变、改变的值与经过核验的材料证据是否对应。用户明确要求先复核时仍要展示待写入内容并等待确认；专用盖章 Skill 的默认直写只省略人为复核，不能省略证据和发布校验。

## 2. 推荐的最小交互

```text
用户上传新 Excel + 材料，或指定已有 Excel 文件名 + 新材料
  → File Agent 唯一定位目标，签发短期 checkout：稳定 ID、当前版本、SHA-256、文件流、表结构
  → WorkBuddy 按实际模板提取信息并生成修改后的 Excel，同时形成单元格变更及证据清单
  → WorkBuddy 一次性回传完整 Excel + 变更清单（可分片上传，完成后一次提交）
  → File Agent 校验来源、目标版本、证据、Excel 差异并原子发布
  → 返回同名文件、Document ID、当前版本、下载地址和逐列回执
```

面向 WorkBuddy 只需要两个主要 MCP 动作：`excel_target_checkout` 和 `excel_result_publish`。后者可在内部使用临时上传会话/分片，但不应让用户手工串联提取、创建数据集、逐列 append、export 多个工具。已存在的文档读取和 OCR 工具仍由 WorkBuddy 按实际可用 Provider 调用；不固定腾讯 OCR。

## 3. 首次创建与后续追加

### 本轮上传新 Excel

新上传的 Excel 优先作为新目标。File Agent 固定上传文件的 Document ID、版本、工作副本 ID、真实文件名、工作表、标题行和布局；同名冲突或多工作表歧义先让用户选定，不静默改名。旧 `.xls` 必须先经受控格式提升为 `.xlsx` 并核对工作表、合并区域、表头、已有行、公式和关键样式；不能保证保真时停止并请用户提供 `.xlsx`。转换后向 WorkBuddy 签发可编辑的当前 `.xlsx` 版本。WorkBuddy只在允许的数据区新增/修改单元格，回传结果。服务端发布后该新目标成为一个可持续追加的普通文件。

### 未上传 Excel、按文件名追加

文件名仅作为查找入口。File Agent 必须在当前用户可访问的服务器文件列表中精确解析：找不到或存在多个同名候选时询问用户；唯一命中后固定 `dataset_id + document_id + working_copy_id + current_document_version_id + current_sha256 + revision`，读取当前工作表、标题和可写区域，并将**当前文件的字节**提供给 WorkBuddy。WorkBuddy从该版本追加，而不是从上次本地缓存或原始上传版重建。回传时携带 checkout 的稳定 ID 和基线版本，服务端执行比较并交换（CAS）；只要文件版本、哈希或数据集 revision 已改变，就拒绝覆盖，重新 checkout 最新版、重新计算拟写入行，并报告冲突。租约只能限制并发时长，不能替代版本比较。

后续仍通过用户看到的同一文件名发起追加；即使用户改名，内部关联的稳定 ID 和版本链不变，工作副本实际 basename、列表展示名和下载名同步改变。新上传 Excel 则开启新的目标，不写回旧表。

## 4. 回传契约与服务器验收

回传至少包含：checkout ID、幂等键、目标稳定 ID 和基线版本/哈希、产物文件 SHA-256 与大小、文件名、工作表及布局、每个变更单元格的旧值/新值、来源 DocumentVersion/提取运行、原文引用及审批/来源状态、是否需要用户复核和确认指纹。Excel 是交付字节；变更清单是可验证的写入声明，不允许两者不一致。

服务端在隔离暂存区接收二进制，验证 MIME/OOXML、扩展名、大小、恶意内容和公式注入风险。解析基线和产物做受控 diff：原有表头、合并区域、工作表、公式、样式、图片/图表、尾注和既有数据不能被非授权改动；只允许本次声明的目标单元格变化或新增行。每个新值须与变更清单一致；按专用 Skill/通用模式复用当前服务端来源快照、逐字证据、真实印章、审批范围、整列条件和 `√` 校验。服务端不重新执行 OCR，也不猜测缺失的证据。若某些 Excel 特性无法可靠比较或 WorkBuddy 编辑器会重写模板结构，拒绝发布，不能以“文件可打开”代替保真。

只有所有来源和全批记录都验收通过，才在目标锁和版本 CAS 下把暂存文件发布为同一个工作副本的当前内容，新增 DocumentVersion、隐藏历史快照、ChangeSet/ChangeItem、ToolInvocation 和数据集 revision/检索索引。失败时丢弃或限期清理暂存件；当前可见文件、版本和已发布数据不变。幂等键重试返回原结果，不重复追加。先发布二进制再提交数据库的跨资源失败要有可恢复发布记录和对账任务，不能产生“数据库完成但文件缺失”的回执。

## 5. 数据集与用户可见文件的关系

推荐把 Excel 当前版本作为表格内容的唯一权威；`structured_datasets` 保留目标绑定、字段/布局、revision、成员来源和查询索引，不再成为另一份可独立重建并覆盖 Excel 的行数据真相。每次成功发布后从已验收的单元格差异更新索引；若索引更新失败，发布流程应回滚或进入可恢复的未完成状态，不能返回成功。现有 `StructuredDatasetExport` 可以继续记录每个 revision 对应的不可变版本，但用户文件列表只展示同名当前工作副本。

保留现有服务端写 Excel 路径作为短期兼容能力，通过显式版本化开关选择旧路径或新路径；同一个任务不得同时使用两条路径，也不得把 WorkBuddy 产物再经过旧 export 重写一遍。切换前应确定旧任务如何继续，以免半途改变写入者。

## 6. 建议实施顺序与验收

1. 定义 checkout、暂存上传、发布回执的 API/MCP schema，以及稳定 ID、版本 CAS、幂等和超时语义。先用合成 Excel 做单人追加、同名冲突和并发冲突测试。
2. 实现受控 Excel diff 与模板保真检查、产物 SHA-256、来源/审批证据绑定；此阶段不改当前写入者。对 `.xlsx`、复杂合并表头和 `.xls→.xlsx` 分别建立黄金样本。
3. 把 WorkBuddy 的编辑与回传接到暂存入口，完成原子发布、DocumentVersion、审计及数据集索引同步。先灰度专用 Skill，再扩展通用 PDF/Word/图片提取。
4. 通过真实文件端到端验收：首次新 Excel、按文件名连续追加两次、用户改名后追加、版本冲突、重复提交、无效印章/残缺审批、只读来源事实、失败不产生表头空文件、列表/磁盘 basename/下载名一致、历史版本可追溯。部署前检查 WorkBuddy 是否具备可靠编辑并回传完整 Excel 的能力；不具备时不能启用新路径。

这一路线减少 WorkBuddy 与 File Agent 之间反复传输字段和驱动多个提交阶段的复杂度，但文件差异、审批证据、并发和版本安全必须留在服务器发布边界；若想让服务器完全不检查直接覆盖，无法满足本项目现有的原件保护、单文件续写和审计要求。
