# 上传新版成果明细表后刷新使用登记余额表

## 用大白话说明

用户上传更新后的《教师成果明细汇总表》，并指定已经发布的使用登记余额表完整文件名。系统按姓名找到余额表中已有的教师。上传表有该教师个人明细页时，优先读取该页 J 列“合计”的资助总额，并用上面的逐项 J 列金额复算；即使上传表“汇总”页的“资助总额（元）”尚未同步，也以已复算的个人页金额更新余额表。没有个人明细页时才取上传表“汇总”页的金额。匹配成功且金额有效时，替换该教师的“总科研成果资助金额”。“总支出”仍然从余额表已保存的逐笔使用登记重新相加，不从成果明细表读取支出，也不重新识别图片。系统用新的资助总额、原有其他资助金额和重新汇总的支出计算剩余金额，并同时更新余额表首页和有登记的个人页左下方。没有登记的教师仅更新首页，不创建空白个人页。

新表中找不到某教师、同名多行或资助额为空/无效时，该教师原资助金额保持不变，回执列为待核对；新表里有但余额表里没有的教师不自动新增。全部都无法安全匹配时停止，不发布空改动。个人页金额复算有效但来源表“汇总”页仍是旧金额时，先只改来源表对应教师的“资助总额（元）”，发布来源表同名新版本；再使用这个新版本刷新余额表并发布余额表同名新版本。两份文件的原版本都保留。

## 实现边界

1. WorkBuddy 用本轮可信附件提交单归档新版 `.xlsx`，取得固定 `document_id`、`document_version_id` 和 SHA-256；目标余额表用完整文件名 checkout，取得当前版本 ID、哈希和 revision。请求不接受任意本地路径。
2. 服务端预览时验证来源是当前已归档 `.xlsx`，目标是已发布的 `funding-usage-v3` 余额表；读取来源“汇总”页作为名单和后备金额，同时按姓名定向读取已有个人成果页的 J 列逐项金额及“合计”。姓名沿用首次生成的精确匹配口径：去掉排版空白后全名相等，不模糊猜测。个人页合计与逐项金额不一致、页结构不对或金额无效时，该人标记待核对，不能退回使用可能过期的汇总页金额。金额按现有非负、有限数值、至多两位小数规则处理。
3. 预览返回逐人旧资助额、新资助额、来源为个人页或汇总页、上传表汇总页原金额、由登记计算的总支出、新余额及无法匹配原因；不改文件。发布须带相同预览指纹，并重新验证来源、目标版本、人员顺序及未完成发布状态。同一请求键重复调用只能返回同一已发布结果，不能重复生成版本。
4. 发布时只改 `funding_usage_funding_v3` 中匹配教师的 `research_total`；保留 `other_total`、逐笔登记 `funding_usage_rows_v3`、来源证据、去重历史和人员顺序。用现有 `summaries` / `render_book` 重算首页与个人页金额；总支出只由登记金额决定。任何登记金额待核对时，该人总支出与剩余金额继续留空。写入同一数据集的新不可变版本，经现有发布协调器同步可见文件。
5. 新增专用 API 与 MCP 的预览/发布工具，并在现有成果资助 Skill 中写明调用顺序；图片追加、人工回传和其他 Excel 流程保持原有入口。测试覆盖匹配更新、无登记人员、待核对支出、重复姓名/无效金额、旧版目标拒绝、版本冲突、重复请求和更新后继续追加/回传。

## 验收口径

- 首页每位教师一行，个人明细原文、日期、金额、序号不变；有个人页的教师左下方金额与首页相同。
- 资助额更新不改变已登记的总支出；新增支出或人工回传后仍按更新后的资助额计算余额。
- 来源表无效或目标版本已变化时不发布；某人个人页合计与逐项金额不符时不更新该人，回执明确列出成功更新与待核对教师，并提供新版本及下载链接。

## 2026-10-19 实测修正

本机样本《教师成果明细汇总（2019-2026）.xlsx》中，金海燕个人成果页的 J 列逐项合计和“合计”格均为 **72,200 元**，同一文件“汇总”页 N 列仍为 **71,000 元**。最初只读 N 列的实现会漏掉个人页修订。现在先把来源表“汇总”页金海燕的 N 列同步为 72,200 元并发布同名新版本，再基于新版本更新余额表。

## 来源表汇总页同步与发布

该流程仅在用户明确要求同时更新来源表和余额表时执行。用户明确说“只更新余额表”时，跳过来源表汇总页预览和发布，直接使用本轮归档来源版本调用余额表刷新预览及发布；个人页金额仍优先于可能过期的来源表“汇总”页金额，来源表本身不生成新版本。提示词指南分别提供两种操作示例。

1. WorkBuddy 对本轮归档来源表调用 `funding_source_summary_preview`。服务端按来源表“汇总”页的姓名逐人查找同名个人页，要求 J 列“合计”恰好一行、数值有效、上方逐项 J 金额之和与它一致。同名汇总行或个人页结构/金额异常只列为待核对；没有个人页的教师保留原汇总金额。预览列出每位教师的旧金额、新金额、行号和状态，不写文件。
2. 有有效差异时，WorkBuddy 用原请求加预览指纹调用 `funding_source_summary_publish`。服务端仅写来源表“汇总”页对应的“资助总额（元）”单元格，保留其他页和字段，创建不可变版本，经现有发布协调器同步同名可见文件。若原版本的存储路径就是可见路径，先复制为隐藏历史版本再覆盖可见文件。重复请求键返回同一版本。
3. 只有来源表返回 `COMPLETED` 且 `excel_published=true` 后，WorkBuddy 才用回执里的新 `document_id/document_version_id/sha256` 调用原 `funding_usage_refresh_preview/publish` 刷新余额表。来源表没有差异时跳过第一步，直接使用本轮上传版本。两个发布分别审计，失败时报告各自状态；来源表已成功而余额表未成功时，不声称两表都更新，用已发布来源版本重新预览余额表即可。
4. 来源表同步只适用于受控成果明细表，不把该表注册成通用按文件名追加的累计目标。个人页与汇总页不一致而个人页复算失败时不改该教师的金额，避免旧 N 值覆盖人工修改。
5. 来源表若含 Excel 公式，本版停止来源表同步并明确报告 `FUNDING_SOURCE_FORMULA_UNSUPPORTED`。当前模板实测没有公式；此保护避免重存工作簿后公式缓存失效。需要支持含公式的模板时，应另行实现保持公式缓存和其他工作表原始内容的定点 OOXML 更新。

## 本地实现记录

使用 `/api/funding-usage/refresh/preview` 和 `/api/funding-usage/refresh/publish`；WorkBuddy 对应 `funding_usage_refresh_preview` / `funding_usage_refresh_publish`。个人成果页优先修复对应插件版本为 `0.1.82`，服务端复用现有数据表、数据集版本和发布协调器，不需要数据库迁移。回归测试还验证了刷新后继续追加图片登记以及下载修改个人页再回传。
