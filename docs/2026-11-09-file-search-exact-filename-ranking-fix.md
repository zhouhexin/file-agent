# 完整文件名精确查找结果被截断的修复

## 现象与原因

服务器存在三份活动《教师成果明细汇总.xlsx》，其共享工作区、当前版本和搜索投影均正确。精确召回能找到三份文件，最终全量结果也包含它们，但位置在第 25～27 位；WorkBuddy 默认请求 `/api/search` 的前 10 条，因此用户看不到目标文件。

`TwoStageFileSearchService._fuse_and_rank()` 在工作副本排序后过早删除 `_score`。合并受管源文件时，`_search()` 再次按分数排序，导致所有工作副本被当作 0 分；同分工作副本随后按 ID 排序，破坏原来的相关度顺序。原有精确文件名加分也不足以保证明确目标进入前 10 条。

排查期间一版诊断脚本误用默认的 `ResolvedSearchScope()`，其默认是空附件严格范围，会得到空结果；该脚本已纠正。不能把这次诊断空结果当成线上索引损坏。

## 修改范围

- 仅修改 `apps/api/app/modules/retrieval/two_stage_search.py` 的排序与内部字段清理时机。
- 工作副本保留融合分数，合并所有检索来源之后再统一排序。
- 按既有文件名规范化规则，将与清洗后查询完整相等的文件名优先，其余沿用融合分数与稳定 ID 排序。
- 不论源侧分支启用、关闭或异常降级，都执行同一排序与分数清理。
- 最终返回前清除两种来源的 `_score`。内部正文匹配标记仍按原有参数控制，不改变证据门槛。

保留所有符合条件的同名独立文件，不自动选择、合并或归档。严格附件范围、年份过滤、正文证据要求、检索候选上限及接口 `top_k` 限制不变。没有修改上传、Excel 读写、余额计算、MCP 或教师查询独立服务。

## 验证

新增回归用例构造三份精确文件名工作副本、12 份普通高分工作副本、14 份高分源侧候选及一份源侧精确文件名候选，验证精确目标在截取前十条前排在最前。覆盖源侧启用、关闭、失败降级，以及普通主题查询中两种来源保留真实分数顺序、返回结果不泄漏分数。

修复前新增测试在排序和前十条保护上失败，修复后检索相关 62 项检查全部通过，覆盖两阶段检索、搜索 API、短语策略、附件范围、第一阶段召回、源侧检索及查询超时恢复。测试使用 SQLite 与确定性替身，未连接服务器 PostgreSQL、未调用外部模型。

## 上线与验收

更新 FileAgent API 后端代码并重建、重启对应 API 服务后生效。没有数据库迁移，不需要重新上传 Excel、重建索引、更新 MCP/WorkBuddy 插件或独立教师查询服务。只复制源码但容器仍运行旧代码镜像时不会生效；按现有代码层发布流程更新。

在 WorkBuddy 查询完整文件名《教师成果明细汇总.xlsx》，应优先返回同名匹配文件。此改动仅保证已召回且通过既有过滤的精确目标优先；若同名匹配本身超过接口返回上限，仍需通过已有选择流程定位，不能宣称一次已显示全部同名文件。

本轮未部署服务器，也未提交 Git；工作区其他既有改动保持原样。
