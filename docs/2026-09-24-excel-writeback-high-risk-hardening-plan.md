# Excel 回传链路高风险加固方案

日期：2026-09-24

状态：代码加固与自动回归已完成；数据库迁移、服务部署及真实 WorkBuddy 会话验证尚未执行。

范围：`/api/excel-writeback`、其 MCP 本地写入/回传入口，以及与之共用同一个累计 Excel 的旧 `structured_dataset_export` 发布路径。旧工具契约和用户可见文件名必须保留。

## 1. 现状与验收不变量

当前回传路径在 `writeback.py` 中先调用 `publish_dataset_current_file` 替换可见工作副本，再由 `runtime.py` 提交数据库。如果替换后数据库提交失败、进程退出或提交结果未知，磁盘和 `WorkingCopy.current_version_id` 可能指向不同版本。旧 `StructuredDatasetService.export` 也有相同的文件先发布问题，不能只修新入口而留下旧入口覆盖同一目标。

当前上传的 32 MiB 限制是在 FastAPI 已解析 multipart 后才检查；候选工作簿先交给 `openpyxl.load_workbook`，随后才检查 ZIP 条目数及解压体积。这两处限制都太晚，不能防止大请求填满临时磁盘或压缩包膨胀占用内存。

发布必须满足以下不变量：

1. `COMPLETED` 回执只在数据库当前 `DocumentVersion`、不可变版本文件、同名可见工作副本、`FileObject` 和导出记录的版本 ID/SHA-256/字节数一致，且本轮记录已提交时返回。任一项不一致都不得报告成功。
2. 目标处于 `PUBLISHING`/`NEEDS_REPAIR` 时，文件列表明确展示状态；当前文件下载、再次追加、重命名、移动和旧导出不得绕过状态读取或修改目标。历史不可变版本仍可用于恢复和有权限的版本下载。
3. 原始上传件永不覆盖。候选和每个发布版本先写入不可变隐藏路径；物理可见工作副本始终使用用户看到的同一 basename，历史不生成多个可见后缀文件。
4. 数据库提交结果未知时不能盲目“回滚文件”；必须用新数据库会话读实际当前版本和持久化发布记录，再决定补发新文件、恢复旧文件或进入人工修复。
5. 文件大小、ZIP 解压量和解析开销在解析前或解析过程中得到有界控制；失败不进入数据集 append/版本发布。

## 2. 高风险一：跨数据库与文件系统发布

### 2.1 增加持久化发布记录

新增迁移 `structured_dataset_publications`（或等价持久表），至少保存：`id`、`task_id`、`dataset_id`、`working_copy_id`、`base_document_version_id`、`base_sha256`、`candidate_document_version_id`、`candidate_sha256`、候选不可变存储路径、同名可见相对路径、状态、重试次数、安全错误码、创建/更新时间。`task_id` 唯一；同一数据集同时只能有一个未终结发布记录。状态建议为 `STAGED`、`DB_COMMITTED`、`VISIBLE_SYNCED`、`COMPLETED`、`NEEDS_REPAIR`，禁止仅凭进程内变量推断阶段。记录中不保存 OCR 全文、候选正文或本机绝对路径。

现有 `StructuredDatasetTask` 仍负责用户预览/确认；发布记录负责崩溃恢复。两个状态必须建立一对一关联。新、旧写入入口共用发布协调器和数据集行锁，不改变旧 MCP/API 名称。

### 2.2 推荐的 DB 优先发布顺序

1. 收取并预检候选后，将完整 XLSX 写入受控的不可变版本候选路径，计算 SHA-256，`fsync` 文件和父目录；创建并提交 `STAGED` 记录。此时不改同名可见文件或数据库当前版本。
2. 在数据库事务中锁定 `StructuredDataset`、`WorkingCopy` 和发布任务，复核 checkout 的基线版本、SHA-256、revision、文件名、工作表与布局；执行已有来源证据/审批/字段校验和成员追加，创建新 `DocumentVersion`、`StructuredDatasetExport`、ChangeSet 审计，更新当前版本及 `active_task_id`，把发布记录和任务置为 `DB_COMMITTED`/`PUBLISHING`，然后提交。此事务**不得**调用同名可见文件替换。旧 `export` 也应改经相同协调器。
3. 数据库提交成功后，使用 StorageService 从已校验的不可变版本原子替换同名可见工作副本；对临时文件和目录执行必要的落盘同步，重新核对可见文件的 SHA-256。失败时保持 `PUBLISHING`，不得返回 `excel_published=true`。
4. 再开短数据库事务，检查当前版本仍为该候选且可见文件哈希匹配，才将发布记录/任务置 `COMPLETED`、释放 `active_task_id`，返回文件名、版本、下载链接和逐文件回执。

数据库已指向候选而可见文件尚未同步的短窗口内，所有当前文件读取和写操作必须由统一门禁返回 `PUBLISHING`/423 或明确待完成状态，不能通过另一下载路由直接读取旧可见字节并称为当前版本。下载实现不能绕过版本和发布状态校验。直接访问服务器磁盘的非 API 读者不具备跨资源事务保证，应在部署说明中明确这一点。

### 2.3 恢复与异常提交

- `STAGED` 且数据库仍指向基线：未进入正式发布。原请求可按同一 task/digest 重试；过期候选在核对无人引用后回收。
- `DB_COMMITTED` 且数据库指向候选：从不可变候选版本重试可见文件发布；若可见文件已是候选哈希，直接执行完成核对。不重新 append，不新增第二个版本。
- 数据库提交抛错或连接断开时，先关闭失败会话，再读实际 `current_version_id` 与发布记录；数据库若已提交则补发候选，若仍为基线则保持/恢复基线。不能把“没有收到 commit 成功响应”当成“事务必然回滚”。
- 数据库、候选版本和可见文件三者互相矛盾，或恢复重试达到上限：标记 `NEEDS_REPAIR`，停止当前文件下载和所有写入，产生结构化告警与管理员对账入口；不得覆盖任一未知内容。
- 恢复器在 API/worker 启动及周期任务中扫描未终结记录，按数据集加锁并幂等执行；同一记录可重试但不能重复写成员、版本或 ChangeSet。

## 3. 高风险二：上传与 XLSX 解压资源耗尽

### 3.1 在 multipart 解析前限制请求体

为 `/api/excel-writeback/tasks/{id}/publish` 增加路径限定的 ASGI `receive` 字节计数，限制**整个请求体**（文件、表单和 multipart 开销），例如初始 34–36 MiB；`Content-Length` 超限立即拒绝，但缺失或伪造该头时仍逐块计数并返回 413。中间件不得先把请求读入内存，也不能仅依赖反向代理配置。反向代理同时设置稍宽但一致的大小限制作为第二道保护。API 业务层保留单文件 32 MiB、`payload_json` 2 MiB 的独立校验。超限时清理已产生的临时上传文件，不创建工具调用或发布记录。

本地 MCP checkout 的下载上限和可发布上限需要一致：超过新链路能力的现有 Excel 应在 checkout 时给出明确的 `WRITEBACK_TARGET_TOO_LARGE`，不能先下载数百 MiB，再在 apply/publish 才失败。

### 3.2 先做有界 OOXML 预检，再调用解析器

抽出共用 `validate_xlsx_package(path, limits)`，在任何 `load_workbook`、全包 `ZipFile.read` 或 XML 全量解析之前调用。至少校验文件实际字节数、ZIP 中央目录/重复名称、条目数、每条及合计声明解压量、加密标记、非法/越界路径、必需 OOXML 部件、宏/可执行嵌入件；按块读取时再次累计**实际**解压字节并校验 CRC，不能只相信中央目录的声明大小。建议首版保守默认值为压缩文件 32 MiB、总解压量 64 MiB、单个 XML 部件 16 MiB、最多 1000 个条目；以真实模板样本和内存基准确认阈值后配置化。超限返回稳定 413/422 错误和可行动说明，绝不进入 openpyxl。

完整差异校验也不得同时把基线和候选所有 ZIP 部件读入两个 `dict`。非目标部件按流计算 SHA-256；目标 worksheet 使用受限 XML 解析并限制行/格数量，复杂模板需要保留原有合并、样式、公式和表格对象校验。若 `openpyxl` 仍用于读取值，应使用适当的只读模式，并在隔离 worker 中设置内存/时间上限；超时或内存超限明确失败，不退回无界解析。对注册新上传 Excel 的旧 `from-excel` 入口也应用同一预检，否则旧路径仍可绕过保护。

## 4. 同轮需要封住的相邻问题

这两项不是前述最高风险的根因，但应和发布加固一起回归：

- 已 `COMPLETED` 的 `preview/confirm/publish` 重试仍必须核对原 `result_digest`、文件 SHA-256 和任务绑定；不同内容返回冲突，不能直接返回旧成功回执。
- `REVIEW_REQUIRED` 若引用尚待确认的 WorkBuddy 文档提取任务，需复用旧任务的 `extraction_confirmations` 校验和确认步骤；只确认 Excel 指纹不能代替来源正文确认。来源未正式归档时保持可恢复等待状态，不无限重试。
- 空模板首次新增数据行不得复制标题样式；新行样式只能继承明确的数据样式行，无法确定时保留普通数据样式或要求布局，不伪装成原模板格式。

## 5. 测试矩阵和上线条件

自动测试必须覆盖：

1. 在候选落盘、`STAGED` 提交、DB 提交前/后、可见文件替换前/后、最终完成提交时逐点注入异常及模拟进程重启；每一点只允许“旧版本可读且任务未完成”或“新版本与数据库一致且任务完成/待恢复”，不能出现错误成功回执。
2. 数据库提交结果未知、恢复器重复运行、两个写入者并发、旧 `structured_dataset_export` 与新回传竞争、重命名/移动同时到达，以及同任务重复提交与不同摘要重放。
3. 超限 `Content-Length`、无 `Content-Length` 分块上传、超量 multipart 表单、ZIP 高压缩比、虚假/重复条目、损坏 CRC、非法路径、宏部件、巨大 worksheet/sharedStrings；断言在 `openpyxl` 前拒绝且没有数据库成员/版本/可见文件变化。
4. 正常 `.xlsx`、复杂布局、公式/图表/其他工作表、空模板、按同名文件连续追加，确认文件列表、磁盘 basename、下载字节、DocumentVersion 和数据集查询一致。

部署顺序：先完成迁移与恢复器，再部署 API/MCP；保持 `WORKBUDDY_EXCEL_WRITEBACK_ENABLED=false`，对已有目标执行只读对账和故障注入测试。确认无未终结发布记录、旧路径回归通过后灰度开启；真实 WorkBuddy 会话分别跑直接保存与先复核路径。出现不一致时关闭新入口、保留发布记录及不可变版本，运行恢复器或人工对账，不能删除目标文件“重试”。

## 6. 实施记录与设计差异（2026-09-24）

已加入 `structured_dataset_publications` 迁移、数据库优先发布协调器、API 启动和 `STRUCTURED_EXTRACTION` worker 空闲/周期恢复、当前下载/查询/重命名和移动门禁，以及文件列表的 `publication_status`。新 WorkBuddy 完整文件回传、旧 `structured_dataset_export`、上传 Excel 首次注册及旧 `.xls` 异步格式提升均在数据库事务内登记候选版本与发布记录；事务提交后才从不可变版本原子同步同名工作副本。涉及旧可见入口的迁移须在新文件哈希核对及旧入口安全清理都完成后才转 `COMPLETED`，清理失败同样可恢复。旧 `.xls` 转换 Job 在物理同步完成前维持 `PUBLISHING`，不提前报告 `COMPLETED`。`COMPLETED` 任务回执会复核当前可见文件和版本关联。旧 Excel 任务仍保留分阶段提交和原 MCP/API 名称。

与 2.2 节推荐顺序相比，实际实现没有单独提交 `STAGED` 数据库行：候选文件先以不可变隐藏路径落盘并校验、同步，然后发布记录 `DB_COMMITTED` 与当前版本/导出记录/成员在**同一数据库事务**中提交。这样提交前故障只可能留下未引用的隐藏候选文件，不会改变可见工作副本；提交后故障必有同事务的可恢复发布记录。未引用候选清理应由后续保留策略处理，不能根据文件名盲删。同步文件失败重试 5 次后转 `NEEDS_REPAIR`，不自动覆盖不明状态。

2026-09-29 补充：针对已绑定任务和基线版本的 `DATASET_VISIBLE_SYNC_FAILED` 增加显式人工补发命令。它要求指定发布记录 ID 和事先核对的可见文件 SHA-256，仅允许可见文件仍等于记录基线或候选版本、候选文件哈希与数据库当前版本一致、任务仍为 `NEEDS_REPAIR` 时恢复；任何未知内容或状态冲突都停止。恢复复用已有 `DocumentVersion` 和发布协调器，不重新 OCR、追加成员或创建导出版本。默认只读对账，`--apply` 才执行；操作命令见 `docs/runbook.md`。

新回传端点使用路径限定的 ASGI 总请求体 36 MiB 上限；基线和候选在 `openpyxl` 前执行 32 MiB 压缩包、64 MiB 总解压量、16 MiB 单 XML 部件、1000 条目和 50000 单元格预检。非目标 OOXML 部件改为流式哈希比较。WorkBuddy 本地 writer 的基线与总解压限制同步收紧；空模板新增行不继承标题样式。`REVIEW_REQUIRED` 的来源确认引用由预览冻结，确认时调用正式来源确认，再在发布前核对来源范围。
